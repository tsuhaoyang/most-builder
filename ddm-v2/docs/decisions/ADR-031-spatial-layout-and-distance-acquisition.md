## 1. 脈絡

### 1.1 動機是量到的，不是推論的

起草本 ADR 時直接讀 `tests/gold/wi_plans/`（正式）與 `tests/gold/wi_plans_draft/`（草稿），得到三項事實：

| 量測 | 數字 | 意義 |
|---|---|---|
| 正式 gold cycle 中，**所有 A 格皆為 `A0`** | **35／35** | `A0` 只在 `reach_cm ≤ 2.5` 時成立。35 條 cycle 全部「伸手不到 2.5 公分」在實務上不可能——這是**文字沒寫距離**，不是真的沒伸手 |
| `total_tmu = 0.0` 的 cycle | 正式 **9** ＋草稿 **2** | 全部 `seq=CM`、`distance_cm=0.0`，M 動詞 `pricing_kind` 全是 `ladder`（`m_push`／`m_pull`／`m_attach`／`m_remove`／`m_teartape`）。距離是唯一貢獻者，距離缺 → 整條 cycle 歸零 |
| 已存在的誠實旗標 | `zero_tmu_distance_unstated` | harvest 階段就標了「complete ≠ 可信 TMU」，本 ADR 是它的後續處置 |

> 量測基準：`tests/gold/wi_plans/`（正式集，35 條有 `tech_line` 的 cycle）於 2026-08-17 的內容。
> 草稿集 `wi_plans_draft/` 當時正被 harvest 重跑重新編號，故草稿的 2 筆只作旁證，**判準以正式集為準**。

**因此的結論（User 判斷，本 ADR 確認其為正確）**：動詞判對、序列判對，**距離不在句子裡**。
這不是 LLM 不夠好，是輸入不含該資訊——再強的模型也生不出不存在的資訊，硬生就是幻覺。
策略是分工：**文字負責「做什麼」，空間佈局負責「在哪裡」**。

### 1.2 但這 11 筆不是同一種缺失——不得整包宣稱「佈局能解」

逐筆看語意後必須切成兩類，否則 Phase B 的驗收會寫成一張假支票：

| 類別 | 案例 | 佈局座標能否供給 |
|---|---|---|
| **物件間位移** | `g10` 推壓合治具至規定位置、`g11` 拉壓合治具、`g12` 推卡扣、`g21` 拉治具底板 | **能**。A 點到 B 點，正是座標的定義域 |
| **動作內行程** | `g17`／`g30`／`g32` 去除包裝袋、`g23` 撕除包裝袋、`g20` 貼附 Label | **不能**。「撕多長」「貼附走多遠」不是兩個物件的間距，是動作自身的行程；座標給不出來 |

動作內行程的正解是**另一種資料**：物件尺寸／包絡屬性，或 IE 認定的動作標準行程值（見選項 E）。
**Phase B 的驗收基準因此是 4 筆，不是 10 筆。** 把 5 筆行程型案例用佈局硬湊出數字，等於製造一個看起來有出處、實際是編的值。

### 1.3 引擎既有的距離入口（三個欄位，不是兩個）

本 ADR 要餵的欄位如下。**注意 A 格用的是 `reach_cm` 不是 `distance_cm`**（`distance_cm` 只存在於 M 格的分量上）：

| 欄位 | 位置 | 引擎換算（`MINIMOST_FACTORY_V2`） |
|---|---|---|
| `reach_cm` | `a0` / `a3`(GM) / `a6` | reach 帶 `≤2.5→0`、`≤5→1`、`≤10→3`、`≤20→6`、`≤35→10`、`≤60→16`、`>60→24`（有 overflow 帶） |
| `foot_cm` | `a0` / `a3`(GM)（**`a6` 禁用**） | foot 帶 `≤20→6`、`≤30→10`、`≤45→16`、`≤65→24`、`>65→32` |
| `distance_cm` | `m3.m_components[]` | M 階梯 `≤2.5→3`、`≤10→6`、`≤25→10`、`≤45→16`、`≤75→24`；**無 overflow 帶** |

由此得出三條**空間模組不得繞過的引擎邊界**（皆已在 `most_engine/calculate.py` 生效）：

1. **A 格取三分量 index 的 `max`，不是相加**（`_a_tmu`）。所以「這段距離算手還是算腳」不是換個欄位那麼單純，見待定參數 P1。
2. **A6 返回格禁 `foot_cm`／`twist_deg`**（`_a_return_tmu` → `A_RETURN_COMPONENT`；ADR-014 E1）。
   佈局若算出「回程超過臂展」，在 A6 **沒有合法表達**——只能報請 IE 裁決，不能改填 `reach_cm`（那是自創語意），也不能歸零（那是靜默低估）。
3. **M 階梯超過 75cm 是錯誤不是飽和**（`ladder_tmu` 回 `None` → `M_DISTANCE_RANGE`）。
   佈局算出 120cm 的「推」，含義是這條動作建模有問題（多半該拆成走動＋推），**不得 clamp 成 75**。

> ［2026-08-17 修訂後的補充］這三個欄位全部發生在**單一作業員伸手可及／腳步可達的範圍內**。
> 這正是新裁決的推導根據：算 TMU 需要的空間資訊，其定義域就是**一個工位**；產線是把工位串起來的排程概念，
> 對 TMU 計算不提供任何額外資訊。

### 1.4 為什麼現在決、而不是等 3D 分頁做出來再說

ADR-012 已 accepted 但未實作。若 3D 渲染先落地並自帶一份場景座標，之後再補距離功能，
必然出現**兩份物件位置資料**（一份給渲染、一份給算距離），且兩份會漂移。
先立「同一份場景資料、兩個消費方向」的不變式，成本近乎零；事後合併則是資料遷移。

## 2. 決策（提案）

### D1 佈局跟工位（站）走；座標編輯入口在「主數據管理」

**［2026-08-17 修訂——原案「佈局跟產線走」作廢］**

> **原案（保留備查，已作廢）**：
> 「**D1 佈局跟產線走；座標編輯入口在「主數據管理」（User 裁決 2026-08-17）**
> 佈局的歸屬單位是**產線**，不是案件也不是 SKU。IE 在主數據管理點開物件、填入座標。
> **入口是既有「主數據管理」頁內的區塊，不是新 tab**——ADR-021／IA 教訓明載「加 tab」是危險信號。」
>
> **作廢原因（User 新裁決 2026-08-17，逐字）**：
> 「假設沒有線，而是一個人站在站上、物件的位置。每一個站都是獨立一個實例，座標是站內相對位置。
> 我們只需要算出 TMU，根本不需要線。」
>
> **推導（本 ADR 確認其為正確）**：§1.3 的三個距離欄位（`reach_cm`／`foot_cm`／`distance_cm`）
> 全部發生在單一作業員的作業範圍內。線是排程／平衡概念（LB 的領域），不是工時計算的輸入。
> 原案把佈局掛在一個「算 TMU 用不到」的實體上，等於為了幾何先建一個排程物件——
> 多一層與計算無關的耦合，而且那個實體（產線）v2 根本還不存在（原 P2 因此存在，現一併作廢）。

**修訂後的決策**：

1. **新增主數據 `stations`（工位）**：`site_id` 必填（工位必屬某廠區；與 `work_vocab_items.site_id` 可為 NULL＝全域的慣例不同——一個「全域工位」沒有意義）。
   **每站是獨立實例**，站與站之間**不存相對位置**（v1 刻意不存，見 D10）。
   歸類：ADR-024 §1 的**主數據**（廠內現況、跟隨現實、無版本、可從外部系統同步），沿用軟刪（`deleted_at`）慣例。
2. **站的原點＝作業員標準站位**。所有座標即「離人多遠」：person→object 距離＝座標長度；object→object 距離＝座標差。
   > **狀態標注（誠實記錄）**：此條是**協調者精煉、User 未反對**，**不是 User 逐字裁決**。
   > 它把「人在哪」從一個待定參數（原 P7）變成座標系的定義本身。殘留問題見 **P10（人端量測基準）** 與 **P11（一站多站位／多作業員）**。
3. **`object_placements` 的鍵改為 `(station_id, object_vocab_id, placement_revision)`**，座標是**站內局部座標**。
   同一物件（例如「料材盒」）在不同站有不同座標，是常態而非例外。
4. **版本化粒度＝「站的擺放修訂」**（取代原 P2 整題）：一個站的擺放是一個可凍結、可標「最後確認日期／確認人」的修訂單位。
   **不存在跨全廠或跨線的「佈局版本」**——那個概念隨產線一起作廢。
5. **入口仍是既有「主數據管理」頁內的區塊，不是新 tab**（ADR-021／IA 教訓明載「加 tab」是危險信號）。
6. **UI 含義（一句）**：**每站一個局部俯視圖即可輸入，不需要先建一張全廠圖。**
   這不是新發明——ADR-022 批次 C 移植的 `ADistanceSelector`（`src/frontend/src/features/workbench-v3/ADistanceSelector.tsx`）
   已經是「以作業員為中心的站內俯視圖」，只是目前用來**選檔**而非**存座標**。

### D2 擺放表與物件身分分離（User 裁決 2026-08-17：「拆表 OK 照你建議」）

- **物件身分沿用既有 `work_vocab_items`**（`kind ∈ object / component / tool / from / to`），**不新建物件表**。
  句子裡的「料架」「工作台」本來就已經是 `kind='from'／'to'` 的詞彙項——它們正是佈局要定位的錨點。
- **新增擺放表** `object_placements`：`(佈局版本, 詞彙項) → x/y/z`，加上取放錨點與備註。
  一個物件可在多條產線／多個佈局版本各有一組座標。
  > **［2026-08-17 修訂］** 本條的鍵改為 `(station_id, object_vocab_id, placement_revision)`（見 D1.3）；
  > 上一行「多條產線／多個佈局版本」應讀為「**多個工位／多個擺放修訂**」。
  > **拆表的理由本身完全不變**——它推導自 ADR-024 §1，與空間單位是線還是站無關。

**決定性理由（可由 ADR-024 §1 直接推出，不是偏好）**：
`work_vocab_items` 是**主數據**——ADR-024 明文「無版本、跟隨現實、可從 MES/ERP/PLM 同步」，
且 `source_system != 'local'` 的列在 v2 是**唯讀**。把需要凍結回溯的座標掛成它的欄位，會同時踩兩個雷：
（a）需要版本的資料寄生在明文無版本的表上，兩種可變性語意打架；
（b）外部同步來源的物件根本寫不進座標。
拆表把「這東西是什麼」與「這東西這一版擺在哪」分開，各自的變動頻率與治理規則才對得上。
**UI 仍維持物件中心**（點物件 → 看到它在各產線的擺放），拆表是資料層的事，不外溢到使用者心智。
> **［2026-08-17 修訂］** 末句的 UI 方向**反轉為站中心優先**：主要輸入介面是「點一個站 → 看到站內所有物件的擺放」（D1.6）；
> 「點一個物件 → 看它在哪些站」仍應提供，但那是查詢視圖，不是輸入視圖。理由：輸入的自然單位是一張俯視圖，一張圖＝一個站。

### D3 臂展內＝手距、超出＝腳步；**閾值數值待 IE 定**（User 裁決 2026-08-17）

分界的**方向**已定：臂展內填 `reach_cm`，超出填 `foot_cm`。
**閾值數值本 ADR 不填**（見待定參數 P1）——並且必須誠實記下：單一閾值二分與引擎的 `max` 語意
不完全相容（風險 R1），P1 可能收斂成「分解規則」而不是「一個數字」。

**閾值的治理歸屬（本 ADR 推導，非 User 裁決）**：它**不是**字典（rule-set）的值——rule-set 管的是
「距離→TMU」的換算表；閾值管的是「這段距離該進哪個欄位」，屬**建模決策**。
依 ADR-027 §1 的版本軸，它的正確歸屬是 **`modeling_policy_version`**（該軸的定義就是
「quantity/tool/SIMO/default 如何 compile」這類非 TMU 值的 compile 決策）。
即使 v1 只用於建議層，**從第一天就記在 `modeling_policy_version` 底下**，日後開自動化時不必改資料模型。

### D4 算出的距離＝**帶出處的建議**，IE 確認才落入 `slot_inputs`（User 裁決 2026-08-17）

- 建議**不是權威**。未經 IE 確認的距離不得寫入 `most_cycles.slot_inputs`。
- **出處不得寫進 `slot_inputs`**——ADR-027 §4 明定 `slot_inputs` 只保存 MOST 計算原始輸入。
  出處存 **`wi_row_contexts`**（既有表，`source='system'`，帶 `schema_version`／`context_hash`）：
  佈局版本 id、來源物件對、量測端點、計算方式（v1＝直線）、閾值政策版本、算出值、IE 是否採納／改值。
  這與 AI 草稿 provenance（`ai_parse_runs` 記 `deployment_bundle_id`）是同一個慣例。
  > **［2026-08-17 修訂］** 出處欄位中的「佈局版本 id」改為 **`station_id` ＋ `placement_revision`**（見 D1.3／D1.4）。
  > 其餘欄位不變。
- 「跑順後再議自動化」——自動化不在本 ADR 的授權範圍內，且開啟前必須先滿足〈重新評估的訊號〉第 4 條。

### D5 距離 v1 走直線（3D 歐氏），避障路徑列為後續

v1 不做繞障、不做人體可達性模型。理由：MOST 的距離帶很粗（2.5／5／10／20／35／60），
在多數工位尺度下繞障與直線落在同一帶；先付路徑規劃的成本不划算。

### D6 座標一開始就存 3D，輸入 UI 可先俯視圖＋高度欄

料架有高度層，`z` 不是可省的裝飾。**存 3D、輸入方式可以二維**（俯視圖點位置＋數字欄填高度）是相容的，
反過來（先存 2D 之後補 z）就是破壞性遷移。

### D7 名詞→物件的對應沿用同義詞治理（ADR-023 模式）

句子裡的「料材盒／料架／流水線」對應到哪個 `work_vocab_items`，走**既有別名層**
`rule_option_synonyms`（ADR-024 §5 已確立：同義詞可指向詞彙庫項，`parameter='vocab'`），IE 核可。
**不新建第二張對照表。**

### D8 分階段（每階段可獨立驗收）

| 階段 | 內容 | 完成判準 |
|---|---|---|
| **A** | 物件註冊（沿用詞彙庫）＋ `object_placements` ＋ 佈局版本 ＋ CRUD／主數據管理 UI | IE 能替一條產線填完一組座標並凍結成一版 |
| **B** | 距離服務（手／腳分界規則）＋ 工作台上的建議值與出處顯示 | 1.2 節「物件間位移」**4 筆**案例能算出建議距離並顯示帶別；行程型 5 筆明確回報「佈局不適用」 |
| **C** | 接 ADR-012 的 3D 分頁：既作座標輸入介面，也作檢視 | 同一份 `object_placements` 同時驅動渲染與距離，無第二份座標 |

> **［2026-08-17 修訂］** Phase A 的內容改為「`stations` 主數據 ＋ `object_placements`（站內局部座標）＋
> **擺放修訂** ＋ CRUD／主數據管理 UI ＋ `wi_rows.station_id`（D9）」；
> 完成判準改為「**IE 能替一個工位填完一組站內座標並凍結成一個擺放修訂，且能把工序表的列指到該站**」。
> 原文的「一條產線」隨 D1 作廢。Phase B／C 不變。
> 這個修訂順帶讓 Phase A 變小：**驗收單位從一條線降為一個站**，第一次交付不必等全廠建模。

### D9 工位綁定在**列**（`wi_rows.station_id`），不在工序表表頭（新增，User 裁決 2026-08-17）

**裁決依據（逐字）**：「一張工時表＝一產品全工序，跨站」。

- **`wi_rows.station_id`：nullable FK → `stations.id`，`ondelete='RESTRICT'`**
  （與該表既有的 `object_vocab_id`／`from_vocab_id`／`to_vocab_id`／`tool_vocab_id` 同慣例）。
  **加法 migration**（ADR-011）：既有列一律 NULL，既有查詢、既有 TMU 計算、既有 gold 期望值皆不受影響。
- **NULL 的語意是「未指派工位」＝不產生距離建議**。
  它**不是**「距離為 0」——後者是 I5 禁止的靜默低估。
- 距離建議**逐列**查該列所屬站的擺放；同一張工序表的不同列查到不同站的座標，是設計意圖而非例外。
- **先例（沿用）**：`02-Memory/RCPSP-Aggregate-Field-Per-Item-Misuse.md`——把「每個成員各異的屬性」
  放在聚合層讀取，是已踩過的坑（`merged_duration_ms` 被當成 per-task 工時，makespan 高估 4 倍）。
  工位在此正是 per-row 屬性；放在 `most_worksheets` 表頭會讓一張跨站的表只能有一個站，
  而「跨站」正是 User 指出的實況。
- **不做**：不因此新增「工序表→站」的聚合欄位（可由列聚合得出的東西不落地，否則兩份會漂移）。

### D10 v1 範圍：只算**站內**距離；**跨站走動不計**（新增，User 裁決 2026-08-17）

- **跨站走動（列 A 的站 → 列 B 的站）v1 不由空間模組計算**；腳步照現行方式由 IE 手填。
  理由（User 裁決）：**多站多作業員是常態**——列與列之間換站，往往是**換人**而不是同一個人走過去。
  把兩站座標之差當成走動距離，是憑空製造一段不存在的位移（且違反 I5 的精神：不得產生沒人知道是假的數字）。
  這也是 D1.1「站與站之間不存相對位置」的直接後果：v1 的資料模型**在物理上無法**算出跨站距離，
  這是刻意的——**讓錯誤的計算不可能，比讓它可能再靠規則禁止更可靠**。
- **單人走整線（cell 生產／一人多站）列為未來**：屆時跨站走動才是同一個人的真實位移，
  需要站與站的相對位置（今天刻意不存）與「這幾站由同一人負責」的資訊（今天不存在）。
  這是**新增資料**而非改既有語意，屬加法。
- **站內腳步（`foot_cm`）仍在範圍內**——但單一原點（D1.2）推不出站內走動距離。
  這個張力是真的，記在 **P11**，不假裝已解。

## 3. 架構不變式（違反即否決）

**I1 — 引擎仍是唯一時間權威。**
空間模組的輸出型別只有**公分**。它不得計算 TMU、不得計算 band index、**也不得為了「對齊帶」而預先取整距離**
（把 33cm 修成 35cm 就是在空間模組裡實作了帶邏輯＝第二條換算路徑）。
可機械檢查：`most_engine/` 以外的模組不得呼叫 `RuleSetData.band_index` / `ladder_tmu` / `foot_tmu`。
建議寫成 CI 守衛（ADR-028 同精神）。

**I2 — 與 ADR-012 共用同一份物件註冊與場景資料。**
`object_placements` 是渲染（asset manifest／擺場）與距離計算的共同來源。
ADR-012 需要的「詞彙→模型」對應（`model_ref`）掛在同一個 `work_vocab_items` 上。**不做兩套場景。**
> **［2026-08-17 修訂］** 共用的單位同步縮為**站**：3D 場景的最小可渲染單元是一個站的擺放修訂，
> 而不是一條線的佈局。這對 ADR-012 是好消息（可 lazy-load 單站），對 I2 的方向沒有影響。

**I3 — 物件命名複用同義詞治理**（D7）。

**I4 — 建議值帶完整出處**（D4）：佈局版本＋物件對＋計算方式＋政策版本，缺一不可。無出處的建議不得顯示。
> **［2026-08-17 修訂］**「佈局版本」讀為「`station_id` ＋ `placement_revision`」。

**I5 — 不得靜默夾擠（本 ADR 新增，對應 CLAUDE.md〈No error bypass〉）。**
算出的距離落在引擎不接受的範圍時——M 階梯 >75cm、A6 出現腳步——
**必須回報「此動作建模需 IE 裁決」，不得 clamp、不得填 0、不得改塞別的欄位**。
這三種「讓它過」的作法都會產生一個沒人知道是假的工時。

**I6 — 「站」的四種語意不得互相冒充（本次新增，2026-08-17）。**
查證後，v2／LB 現存四個都叫 station 的東西，語意互不相同：

| 出處（已查證） | 型別與語意 |
|---|---|
| `most_engine/level.py`（Level System → LB 輸出合約） | `groups[].same_station`（cub 同站不可拆）、`number_constraints[].kind='max_per_station'`——**排程約束**：這些動作必須／不得被分到同一個 LB 工站。**與幾何完全無關** |
| LB `multi_line_solver/domain/models.py::Station` | `id: int`、`position: int \| None`——**線上的第幾個工站**（整數序位）。無公制、**無字串代碼欄位** |
| `nlp/contracts.py::ParseContext.station_hint` | `str \| None`——AI 解析上下文的**自由文字**提示，非 FK，無參照完整性 |
| 本 ADR 的 `stations` / `wi_rows.station_id` | **幾何實體**：一個作業員的實體工作範圍，帶站內局部座標系 |

規則：新欄位一律用 `station_id`（FK→`stations`），並**在模型宣告旁以註解固化合約**；
不得把 LB 的序位、level 的約束值或自由文字寫進這個欄位。
**先例（沿用）**：`02-Memory/RCPSP-Index-vs-TaskID-Contract.md`——`list[int]` 同時可以是 index 與 id，
型別系統擋不住，104 個測試全綠仍靜默錯誤；教訓是「橋接層是 contract boundary，
任何轉換都要在欄位旁標注，不依賴呼叫方記憶」。此處四種 station 的碰撞面比當時更大，
因為它們**跨兩個 repo**。

## 4. 考慮過的選項

**A. 座標直接掛 `work_vocab_items` 欄位**（User 原始提案）
最少的表、最直觀的 UI 對應。**取捨**：同一物件在多條產線只能有一組座標；佈局無法版本化，
改了就沒有舊值，回溯只能靠 audit log 拼；且與 ADR-024「主數據無版本、可被外部系統唯讀同步」直接衝突，
外部來源的物件寫不進座標。→ **User 2026-08-17 經取捨後改採拆表（D2）。**
> **［2026-08-17 修訂］**「多條產線」讀為「多個工位」。站模型讓這個否決理由**更強**：
> 工位數遠多於產線數，一物件一座標的限制會更早爆掉。

**B. 座標塞 `process_versions` 的 JSONB（ADR-011 §5「先軟承接」）**
最快、零 schema 風險。**否決**：佈局是產線層級的共用事實，塞進案件會讓同一條線的 N 個案件
各自維護一份、彼此漂移；而且 JSONB 內的物件參照沒有 FK，物件被軟刪後成為孤兒參照。
（ADR-011 的「軟承接」適用於**尚未定義形狀**的欄位，不適用於已知會被多方共用的實體關係。）
> **［2026-08-17 修訂］**「產線層級的共用事實」讀為「**工位層級**的共用事實」——
> 同一個站會被多個產品／多個 ProcessVersion 使用，共用性甚至比原本設想的更高。否決結論不變。

**C. 從 CAD／廠房圖直接匯入座標**
真實工廠已有圖檔，理論上不必手填。**不作為 v1 起點**：檔案格式偵察成本高（先例：
`Third-Party-Field-Format-Reconnaissance`）、圖檔的物件粒度與詞彙庫粒度幾乎必然對不上，
需要的仍是 D7 的別名對應層。作為 Phase A 之後的匯入器加值，不改變本 ADR 的資料模型。
> **［2026-08-17 修訂］** 站模型進一步降低此選項的優先度：廠房圖給的是**全廠佈置**（哪個站在哪），
> 而本 ADR v1 需要的是**站內擺放**（料架離人多遠）——後者多半不在廠房圖裡，得現場量。

**D. 讓 LLM 從上下文猜距離**
**明確否決**。1.1 的量測已證明資訊不在輸入裡；猜出來的數字會帶著 AI 的 provenance 進入 gold set，
污染唯一的評測基準（gold set 目前正是靠 `zero_tmu_distance_unstated` 誠實旗標守住這條線）。

**E. 不做座標，只做「動作標準距離表」**（每個 M 動詞／每類動作給一個 IE 認定的預設 cm）
**這是最便宜的止血，而且是 1.2 節那 5 筆「動作內行程」案例的唯一解**——撕除包裝袋的行程本來就不是佈局距離。
**但它解不了物件間位移**（同一個「推至規定位置」在不同工位距離不同），
且單獨採用會把假精度固化成看似權威的預設值。
→ **建議：E 與本 ADR 並存，分工明確**——物件間位移走佈局，動作內行程走標準值，兩者的 provenance 分別標示。
E 的規格不在本 ADR 範圍，列為後續（P5 裁決後才知道邊界畫在哪）。

**F. 擺放表與物件身分分離（選定，D2）**
代價是多一張表、多一層版本概念、UI 要自己把兩者拼回「物件中心」的畫面。
換得：同物件多線、佈局可凍結回溯、身分與位置各自照自己的頻率變動、與 ADR-024 的分界一致。
> **［2026-08-17 修訂］**「同物件多線」讀為「同物件多站」。

**G. 新增 `production_lines` 實體作為佈局歸屬（本 ADR 原稿的傾向，2026-08-17 作廢）**
原稿的 P2 傾向新增產線實體。**否決理由（User 裁決）**：TMU 計算不需要線，
新增一個計算用不到的主數據實體，卻要付 RBAC／匯入／LB 契約三份代價。
線若日後真的需要（LB 對接、報表分組），是**另一個 ADR 的題目**，且屆時它是「站的集合」，
可以加法引入而不動本 ADR 的座標模型——**先做站再做線的回頭成本，遠低於反過來**。

**H. 工位綁在工序表表頭（`most_worksheets.station_id`）而非列（2026-08-17 淘汰）**
較少的欄位、UI 只要選一次。**否決**：與實況直接矛盾——一張工時表是一個產品的全工序，會跨站（D9 裁決依據）。
綁表頭會逼出兩種壞結果之一：要嘛一張表被迫拆成 N 張（破壞「一產品一工序表」的既有模型與 1:1 對 `process_version` 的約束），
要嘛整表共用一個站的座標而產生系統性錯誤距離。先例見 `RCPSP-Aggregate-Field-Per-Item-Misuse`。

## 5. 後果

**資料模型（加法，合 ADR-011）**：新增 `object_placements` 與佈局版本表；
`work_vocab_items` 可能加 `model_ref`（ADR-012 需要，屬加欄）。既有查詢不受影響。
> **［2026-08-17 修訂後的完整清單］**
> （a）新增 `stations`（主數據，site-scoped，軟刪）；
> （b）新增 `object_placements`，鍵 `(station_id, object_vocab_id, placement_revision)`，站內局部 3D 座標；
> （c）新增擺放修訂表（或以 `placement_revision` ＋ 凍結欄位承載，形狀屬實作決定）；
> （d）`wi_rows` 加 `station_id`（nullable FK，RESTRICT）——**加法**，既有列全 NULL；
> （e）`work_vocab_items` 可能加 `model_ref`（ADR-012）。
> 原文的「佈局版本表」（跨線層級）不再需要。

**回放語意（重要，且與直覺相反）**：
因為建議值最終是以**公分數字**落進 `slot_inputs`，回放一條 cycle 只需要 `slot_inputs` ＋ `rule_set_id`
就能重現 TMU——**佈局版本不進回放路徑**。它進的是**稽核路徑**：回答「這個 45 公分當初哪來的」。
兩者不可混為一談（ADR-027 §1：版本軸不得互相冒充）。
**但這個性質完全依賴「IE 確認才落值」這個前提。** 一旦開自動化，佈局版本與閾值政策就變成計算路徑的成員，
屆時必須升格為 ADR-027 §1 的正式版本軸並補寫回放規則——見〈重新評估的訊號〉第 4 條。
> **［2026-08-17 補充］** `wi_rows.station_id` 同理**不進回放路徑**：它是「這列發生在哪」的事實標注，
> 不是 TMU 的輸入。這一點必須寫進欄位註解，否則日後很容易被誤讀成計算輸入而被塞進 `slot_inputs`（違反 ADR-027 §4）。

**與 LineBalance 的關係（unified-arch 待辦，本 ADR 不逕自定義）**：
LB 已有 `Station`／`line_station_positions` 概念，但查證其領域模型後可確認——
**LB 的 `Station.position` 是「線上的第幾個工站」的整數序位，不是公制座標**。
兩者不是同一個東西，**不得互相冒充**。方向維持既有分工：**MOST 定義產線／工站身分與幾何，LB 消費**；
需要一組共享的 line／station 外部碼，且共享契約以**單一文件**為準，不兩邊各寫一份。
此事項需 unified-arch 協調，**不在本 ADR 決定**。
> **［2026-08-17 修訂］** 上段中「MOST 定義**產線**／工站身分與幾何」的產線部分作廢（隨 D1）。
> 修訂後的分工是：**MOST 管幾何（站內物件在哪），LB 管排序（哪些動作分到第幾站）**。
> 完整說明見下一節。

### 5.1 LB 重平衡會改變工時——本 ADR 第一次讓它可計算（本次新增，2026-08-17）

**因果鏈**：LB 重平衡＝把動作從 A 站搬到 B 站 → 該動作面對的物件相對位置改變 →
`reach_cm`／`foot_cm`／`distance_cm` 改變 → **TMU 改變**。
也就是說，**LB 消費的工時，會被 LB 自己的決策改變**。

**今天的狀態**：這是 IE 的**隱性知識**（「搬過去要重估工時」全靠人記得、靠經驗估）。
系統裡沒有任何地方表達這件事，因此也沒有任何地方會提醒它被遺漏。
站級座標模型第一次讓這個量**可計算**——這是站模型相對於線模型的實質收益，不只是資料整潔。

**v1 明確不做回饋迴路**（LB 排完 → MOST 自動重算距離與 TMU）。理由：
迴路成立的前提是「目標站的擺放已存在」與「跨站位移可算」，兩者 v1 都不具備（D10）；
而且未經 IE 確認就重算 TMU 會直接違反 D4（建議非權威）。

**但 D9 的列級站綁定就是這個迴路的對接口**：LB 的輸出（哪個動作分到哪個站）
能落回 MOST 的**哪一列**，這條線今天就接上了；日後開迴路不必改資料模型，只需新增計算與確認流程。
這是本次修訂裡回頭成本最低的一步——一個 nullable 欄位換掉一次資料遷移。

**對接方式（歸 unified-arch，本 ADR 不決定）**：
LB 的 `Station`（整數序位）與 MOST 的 `stations`（幾何實體）以**共享工位代碼**對接。
職責分工：**MOST 管幾何、LB 管排序**。
這比原稿的「產線對接」**更乾淨**——雙方不需要對「線」這個實體達成一致，只需要對「站」的識別碼達成一致。

> **查證到的實作缺口（給 unified-arch 的事實，不是決策）**：
> LB 現行 `Station` 只有 `id: int` 與 `position: int | None`，**沒有字串代碼欄位**；
> `Worker.station_id: int` 也是整數。因此「共享工位代碼」不是把兩邊現成欄位對起來就好，
> 需要 LB 端加欄或在 pipeline adapter 明確映射，且該轉換必須照 I6 的規則標注。
> 共享契約以**單一文件**為準。

**前端**：主數據管理內新增佈局區塊（非新 tab）；工作台的距離欄位旁顯示建議值與出處徽章；
Phase C 的 3D 分頁依 ADR-012 lazy-load。前端交付照既有規矩：typecheck ＋ build ＋ 截圖對照 v3 ＋ code-reviewer。
> **［2026-08-17 補充］** 座標輸入的形狀是**每站一張局部俯視圖**（D1.6），不需要全廠建圖。
> 既有的 `ADistanceSelector`（ADR-022 批次 C 移植自 v3）已經是站內俯視、以作業員為中心的極座標畫面，
> 是這個輸入介面最接近的既有母版。
> **但要注意一個不一致**：該元件的同心弧圓心是**肩關節**（原始碼註解：「照 v3：400×340，肩關節中心 (200,280)」），
> 而 D1.2 把座標原點定在**站位**。兩者差一個人體幾何常數——見 P10，這不是可以「畫得差不多就好」的細節。
> 工作台的列上另需一個**工位選擇器**（D9），且未指派時要明確顯示「未指派工位＝無距離建議」，不得留白讓人以為沒距離。

**gold set**：Phase B 以 1.2 節的 4 筆物件間位移案例為第一批驗證；
補上距離後這些 cycle 的 `expected_cycles` 需由 IE 重新核可（改動 gold 期望值必須走覆核流程，不得由實作者直接改）。
另需注意：**35／35 的 A 格為 0 是比 11 筆歸零更大的系統性低估**，佈局上線後 gold set 的期望值會**整批**變動——
這是一次需要 IE 排程的重新基準化，不是順手改幾個檔。

**代價**：多一套需要人維護的主數據（風險 R3）；建議層多一次 IE 點擊；
`wi_row_contexts` 的 `context_data` 需定義 spatial 子 schema 並納入 `schema_version` 治理。
> **［2026-08-17 補充］** 站模型把維護單位從「線」細分為「站」，**維護面積 = 站數 × 站內物件數**，
> 比原案大一個量級（見 R3 的修訂），並且新增一項人工輸入：每列要指派工位（D9）。
> 這是站模型的真實代價，不應被「模型更乾淨」蓋過去。

## 6. 待定參數（本 ADR **不**擅自填值）

| # | 參數 | 為什麼不能猜 |
|---|---|---|
| **P1** | **臂展閾值，以及「距離如何分解成 reach／foot」的規則** | 引擎 A 格取 `max(reach, twist, foot)` 而非相加；且 `foot_cm` 的語意是「腳移動的距離」不是「總位移」。若把 150cm 整包塞進 `foot_cm`，得到 foot 帶 32；若拆成「走 130cm ＋ 伸手 20cm」則是 `max(32, 6)=32`；若拆成「走 100 ＋ 伸手 50」則 `max(32,16)=32`——多數情況殊途同歸，但邊界附近不是。IE 必須定的是**分解規則**，單一閾值可能只是它的特例 |
| **P2**（**［2026-08-17 修訂］整題作廢，原文保留備查——見 §6.1**） | **佈局版本化的粒度：新增 `production_lines` 實體 vs 掛 `ProcessVersion`** | 現況 v2 **沒有產線實體**（階層是 Site→Product→SKU→ProcessVersion）。**本 ADR 的傾向是新增 `production_lines`**（理由：User 說「佈局跟產線走」；掛 ProcessVersion 會讓同線多案件各存一份；LB 的 line 概念需要一個對應錨點）——但這是**新增一個主數據實體**，影響 RBAC、匯入、LB 契約，應由 User 明示 |
| **P3**（**［2026-08-17 修訂］部分已定**） | 座標原點與軸向約定（原文：「每條線一個局部座標系 vs site 全域」；原理由：「決定跨線複製佈局的可行性，以及 3D 場景如何拼接」——**兩者隨 D1 作廢，改讀為站**） | **原點已定**：每站一個局部座標系，原點＝作業員標準站位（D1.2，**協調者精煉、User 未反對**）。**仍待定**：軸向約定（哪個方向是 +y／作業員面向）、單位（本 ADR 假設 cm，與引擎欄位一致，需 IE 確認）、以及同型站之間座標系是否可對齊以便複製（見 P9） |
| **P4** | 量測端點：物件中心 vs **取放錨點** | 料架有高度層 → 中心點會給出無意義的距離；取放錨點才是手真正去的位置。可能需要一個物件多個錨點 |
| **P5** | **M 的 `distance_cm` 語意：動作內行程 vs 物件間位移** | 直接決定 1.2 節的分類邊界。`g20`（從料材盒拿 Label 貼附至主板）兩種讀法都說得通，IE 一句話定生死 |
| **P6** | 雙手／SIMO 的距離歸屬 | 兩隻手到不同物件時，一條 cycle 的距離取哪一個（ADR-020 的貢獻語意不涵蓋距離） |
| **P7**（**［2026-08-17 修訂］大部分已被 D1.2 吸收**） | 作業員站立位置是否也進擺放表 | 原理由（保留備查）：「距離是『人到物』還是『物到物』——若是前者，人的站位就是必要的擺放項」。修訂後的答案：**站位不是擺放項，而是座標系原點本身**（D1.2）。殘留的真問題移入 **P10／P11** |
| **P8**（新增） | **`stations` 的識別與外部碼**：`external_code` 的唯一性範圍（如 `sites`／`work_vocab_items` 的全域 unique，還是 site 內 unique）、以及它是否即為與 LB 對接的共享工位代碼 | 外部碼一旦發出去給 LB／MES 就很難改。全域 unique 在多廠區會撞名（「工位 A01」每廠都有），site 內 unique 則跨廠引用時必須帶 site——兩種都可行但契約不同，且直接影響 §5.1 的 LB 對接。**歸 unified-arch 協調** |
| **P9**（新增） | **同型站是否需要「站型樣板」**：N 個配置相同的站，要各填一份座標，還是有 station_type 樣板＋每站覆寫 | 這決定維護面積是 O(站數×物件數) 還是 O(站型數×物件數)。R3（過期資料）是本 ADR 最可能致命的失敗模式，而站模型把維護面積放大了一個量級——若現場多半是同型站，樣板可能是 R3 的關鍵緩解；若每站都不同，樣板只是空複雜度。**這需要現場事實（同型站佔比），不能推理** |
| **P10**（新增） | **人端的量測基準**：站位（腳）／肩關節／手的初始位置 | `reach_cm` 的物理定義是手伸出去的距離，起點在肩；D1.2 把座標原點定在站位（腳）。兩者差一個人體幾何常數（隨前傾程度變動）。已查證：現行 `ADistanceSelector.tsx` 的同心弧圓心是**肩關節**（`肩關節中心 (200,280)`），與 D1.2 不一致。不定義的話 `reach_cm` 會**系統性偏一個固定量**——而且是恆定偏差，最不容易被抽查發現 |
| **P11**（新增） | **一站多站位／多作業員**：（a）雙人站——一個站有兩個原點，`object_placements` 的座標對誰量？（b）同一人在站內有兩個以上標準站位（例如機台與工作台之間來回）——單一原點推不出站內走動距離，但 D10 又把站內 `foot_cm` 留在範圍內 | 這是 D1.2「單一原點」假設的邊界。若現場存在（b），站的模型需要「站內多個作業點」而不是一個原點——那是資料形狀的改變，愈晚發現愈貴。**本 ADR 不擅自擴 scope 去支援它，但也不假裝它不存在** |
| **P12**（新增） | **`station_hint`（NL parse 自由文字）與 `wi_rows.station_id` 是否收斂** | `nlp/contracts.py::ParseContext.station_hint` 已存在且是自由文字（I6）。若兩者長期並存而不收斂，就是兩套站資料各自漂移；若要收斂，解析階段應走 D7 的別名層把 hint 對到 `station_id`。屬加法，但要先決定方向 |

### 6.1 P2 作廢紀錄（［2026-08-17 修訂］）

**作廢原因**：P2 問的是「佈局版本化的粒度：新增 `production_lines` 還是掛 `ProcessVersion`」。
User 新裁決取消了問題的前提——空間單位是**站**，兩個候選皆不成立（見 D1 的作廢說明與選項 G）。

**取代它的答案**：版本化粒度＝**站的擺放修訂**（D1.4）。一個站的擺放是一個可凍結、可標最後確認日期／確認人的修訂單位。

**未被取代的殘留**：原 P2 提到「LB 的 line 概念需要一個對應錨點」——這一點**仍然為真**，
但錨點改為**站**（§5.1），且歸 unified-arch。若 LB 日後確實需要 line 實體，那是另一個 ADR（選項 G）。

## 7. 風險

**R1 — 單一閾值二分可能是過度簡化的模型**（見 P1）。
若 IE 定出的規則其實是分解規則，D3 的敘述需改寫。緩解：v1 的閾值只用於**建議層**，IE 每筆都會看到，
錯誤模型會在使用中被人抓到，而不是靜默污染資料。

**R2 — 假精度。**
3D 座標會讓人以為距離很準，但引擎的帶很粗（2.5／5／10／20／35／60）。
座標誤差 5cm 有時完全無影響、有時跨兩帶。
緩解：UI 顯示「落在哪一帶、距帶邊界多遠」，讓 IE 看得到自己站在懸崖邊還是平地。

**R3 — 佈局資料無人維護就變成過期資料，比沒有更糟。**
工廠佈局會改；一份沒跟上的座標會產生看似有出處、實際錯誤的距離。
緩解：佈局版本帶「最後確認日期」與確認人；超過期限的佈局所產生的建議必須降級顯示（或拒絕產生建議）。
**這一條是本 ADR 最可能致命的失敗模式**——選項 E（標準距離表）之所以留著，正是因為它沒有這個維護負擔。
> **［2026-08-17 修訂——風險升高，不是降低］** 站模型把維護單位從線細分到站：
> 維護面積由 O(線數×物件數) 變成 **O(站數×物件數)**，大一個量級。
> 緩解手段相應細化：（a）確認日期與確認人掛在**擺放修訂**上（D1.4）；
> （b）**P9 的站型樣板**若成立，可把面積壓回 O(站型數×物件數)——這使 P9 從「optimization」升格為 R3 的主要緩解；
> （c）Phase A 的驗收單位是一個站（D8 修訂），可以先在一個站上量測真實維護成本，再決定要不要鋪開。
> **(c) 是本次修訂帶來的意外好處：站模型讓這個最致命的風險變得可以小規模試錯。**

**R4 — 與 ADR-012 的耦合過早。**
Phase C 才真正接 3D，但 I2 現在就約束了資料形狀。若 ADR-012 實作時發現渲染需要的座標系與距離需要的不同
（例如渲染要模型原點、距離要取放錨點），需在同一張表上並存兩組錨點，而非分裂成兩份場景（P4 先處理可降低此風險）。

**R5 — 「建議」退化成「預設」。**
IE 一路按確認，等同自動化上線卻沒有經過自動化該有的把關。
緩解：量測採納率與改值率（沿用 `ai_review_events` 的同一套回饋概念），
採納率異常高（例如 >95% 且改值率近 0）應視為需要覆核的訊號，而不是成功指標。

**R6 — LB 重平衡後 MOST 的距離沒跟著更新（本次新增，2026-08-17）。**
§5.1 的因果鏈今天就存在，只是隱形。站模型讓它可計算，但 v1 不做回饋迴路——
於是會出現一個新的失效模式：**LB 已經把動作搬到 B 站，MOST 的列仍指著 A 站**，
距離建議與已落值的 TMU 都是舊站的。這比「沒有距離」更糟，因為它看起來有出處。
緩解：（a）`wi_rows.station_id` 變更時，該列既有的空間來源建議必須標記為 stale（出處在 `wi_row_contexts`，可查）；
（b）在開回饋迴路之前，**不得**由 LB 端寫入 `wi_rows.station_id`（單向：MOST 是站綁定的權威）。
這兩點屬實作約束，寫在此處以免被遺忘。

**R7 — 「站」的四種語意在跨 repo 的邊界上被混用（本次新增，2026-08-17）。**
見 I6。LB 的整數序位、level 的排程約束、`station_hint` 的自由文字、本 ADR 的幾何實體，
四者在對話與程式碼裡都叫「station」。先例（`RCPSP-Index-vs-TaskID-Contract`）顯示這類混用
**可以在 104 個測試全綠的情況下靜默存在**，且只有 code review 抓得到。
緩解：I6 的欄位註解規則；LB 對接的轉換點必須有明示映射（P8）。

## 8. 重新評估的訊號（proposed 必填）

1. **IE 定出的分界規則不是「單一閾值」** → D3 與 P1 重寫，可能連 `foot_cm` 的填法都要改。
2. **Phase A 上線後佈局資料的過期率高於 IE 可接受水準**（R3 成真）→ 退回選項 E，佈局降級為純視覺化資產。
3. **ADR-012 先落地且已自帶一份場景座標** → I2 的共享方向反轉（改由渲染側的場景定義為準），本 ADR 的資料歸屬需重議。
4. **要開自動化（建議不經 IE 確認直接落值）** → 本 ADR「建議非權威」的前提失效；
   佈局版本與閾值政策成為計算路徑成員，必須升為正式版本軸並補回放規則。**此時本 ADR 必須被新 ADR 取代，不得默默改行為。**
5. **LB 需要的是幾何而不只是序位** → 共享 line／station 契約必須提前，且由 unified-arch 統一定義。
   > **［2026-08-17 修訂］** 契約的主體改為**站**（§5.1）；且已知 LB 端缺字串代碼欄位（P8），
   > 這個訊號一旦出現，工作量比原稿估計的大。
6. **量到「物件間位移」型案例佔比遠低於預期**（真實 WI 大多是動作內行程）→ 佈局的投資報酬需重算，選項 E 應優先。
7. **（新增）出現單人走整線（cell 生產／一人多站），或站內存在多個標準站位**（P11 成真）→
   D10「跨站不算」與 D1.2「單一原點」同時失效，站的幾何模型需要「站內多作業點」與「站間相對位置」，
   屬資料形狀變更，必須新開 ADR 而非在此改字。
8. **（新增）LB 提出重平衡後自動重估工時的需求**（§5.1 的回饋迴路）→
   D10 的「跨站不計」與 D4 的「IE 確認才落值」同時受壓；此時需先回答訊號 4，再談迴路。
