# 文件分類法 (Document Taxonomy)

## 0. 為什麼需要分類

文件不是一種東西。把「當時的決定」和「現在的事實」混成同一份檔案，
結果只有兩種，兩種都壞：

| 混法 | 後果 |
|---|---|
| 決策紀錄被改寫成現況 | 失去歷史。沒人知道為什麼當初否決了方案 B，於是方案 B 被重新提一次 |
| 規格留著舊敘述 | 變成**假權威**。agent 讀到就當現況，照著舊契約寫新程式 |

第二種更貴，因為它不會報錯。

> 文件的讀者有一半是 agent。Agent 沒有記憶、不會質疑語氣，
> **它讀到什麼就當成現況。**

所以每一類文件都必須明確回答三件事：**它的時態是什麼、能不能被引為實作依據、誰可以改它。**

## 1. 九類文件

照追溯鏈的順序排（`REQ → DESIGN → ACC → TICKET → TASK`，`stage-table.md` §7）：

| 類別 | 回答什麼問題 | 時態規則 | 可否引為**實作依據** | 誰可改 |
|---|---|---|---|---|
| **SPEC** | 這個元件**現在**的契約是什麼 | **只寫現況**，就地改寫 | ✅ **唯一權威** | doc-sync，human 核可後 |
| **REQ** | 這張票**要達成什麼** | 未來時態，**凍結於 DESIGN 定案** | ⚠️ 只能被 `design` 與 `acceptance` 引；**`implement` 不得引** | analyst，定案後需 human |
| **DESIGN** | 這張票**要怎麼做** | 未來時態，**凍結於 ACC 定案** | ✅ **`implement` 的唯一依據** | architect，定案後走重新核可（§1.9） |
| **ACC** | 怎樣算做到了 | 綁 DESIGN hash，定案後凍結 | ✅ **驗收的唯一依據** | **verifier 提案**，**human 核可** |
| **TICKET** | 哪裡有缺口、誰在處理、做完了沒 | 描述檔凍結 + 交棒檔改寫（§1.5） | ❌ | orchestrator |
| **ADR** | 我們**當時**為什麼選 X 不選 Y | **凍結在決策時**，只追記不改寫 | ⚠️ 只能引「決策」，不能引「現況」 | doc-sync，追記 |
| **DOMAIN-INDEX** | 這個領域有哪些 SPEC / ADR / TICKET | 只寫現況 | ❌ 只是路由 | doc-sync 或腳本 |
| **PROCESS-RECORD** | 我們當時**怎麼想**的（規劃書、討論紀錄） | 凍結，**必標 SUPERSEDED** | ❌ **明文禁止** | 不改 |
| **LOG** | **什麼時候發生了什麼** | **追加,永不改寫既有條目** | ❌ 只是紀錄 | 任何角色，只能 append |

> **REQ 與 DESIGN 是 v0.5.0 新增的**（規則本體在 §1.8 / §1.9）。
> 章節編號接在尾端、不插在 SPEC 之後：重新編號會讓既有每一處 `§1.x`
> 交叉引用同時失效，而那正是 §8.1「anchor 用標題不用行號」要避免的漂移。
> **上表是閱讀順序，章節編號是歷史順序，兩者刻意不一致。**

### 1.0 類別必須在檔頭宣告——目錄不是判準

每份文件的檔頭**必須**有 `類別:` 欄位，值為上表九類之一。
檔頭用 **YAML frontmatter** 宣告：檔案第一行是獨立成行的 `---` 開界，接鍵值行，
再以第二個獨立成行的 `---` 閉界：

```markdown
---
類別: <SPEC / REQ / DESIGN / ACC / TICKET / ADR / DOMAIN-INDEX / PROCESS-RECORD / LOG>
狀態: <依類別適用的狀態詞彙，見 §1.1>
---

# <標題>
```

> frontmatter 只是檔頭**表示法**（由早期的 blockquote 引言區塊遷移而來）；
> 它不改「必須宣告類別」「狀態詞彙」「hash 排除標頭」任一語意。
> hash 正規化把整個 frontmatter 區塊當標頭排除，界線見 `stage-table.md` §8.2。

**不得用目錄推斷類別。** 實跑證據：某專案 `docs/architecture/`（慣例上是過程紀錄目錄）
底下存在一份開頭寫著 "Architecture Spec … this file is the single source of truth"
的文件——它功能上是 SPEC，住在 PROCESS-RECORD 目錄裡。
用目錄判類別會把它誤判成不可引用的歷史文件，反之也會把施工圖誤讀成規格。

#### 非 markdown 文件的宣告寫法

`類別:` 原本只寫了 markdown 的形式，但受管的文件不全是 markdown
（交棒檔是 YAML、索引可能是腳本產生的 YAML）。第一行註解即可：

```yaml
# 類別: TICKET（交棒檔）
# 狀態: 見 state 欄位
```

> 這是 v0.5.0 dogfooding 撞出來的：第一次要寫一份真的交棒檔時，
> §1.0 要求宣告類別，而它的語法只定義了 markdown 的 blockquote 形式。
> **C2（缺類別宣告 → 擋）對 YAML 檔無從執行**，
> 於是整個票庫會剛好落在檢查覆蓋之外——而票庫是 C21–C27 全部七條的輸入。

**不能加任何檔頭的 .txt／.log**（逐位元組照抄的副本、程式輸出，加 frontmatter 或註解
都會污染逐字內容）：類別宣告寫在**同目錄 README 的清單**——該目錄 README（本身有
frontmatter）列出目錄內各 .txt／.log 檔及其類別（多為 PROCESS-RECORD 或 LOG）。
這是「要宣告類別」語意的既有延伸，不是新義務：宣告位置從檔內移到同目錄 README。

目錄是慣例，`類別:` 欄位是判準。機械檢查因此變成兩條：

1. 類別已宣告
2. **被引用的方式與宣告的類別一致**（`process_record` 不得被當作實作依據引用）

#### 模板的類別寫法

模板寫 `類別: TEMPLATE → <產出類別>`，例如 `TEMPLATE → ACC`。

**`TEMPLATE` 不得被引為任何依據**，它只定義產出物的形狀。
複製出來的實例才改成產出類別本身。

> **這是 dogfooding 自我檢查撞出來的：** `templates/ACC.md` 原本宣告 `類別: ACC`，
> 而 ACC 是「驗收的唯一依據」——
> 一份模板不該能被當成任何東西的驗收依據。
> 但也不該為此新增第八類：模板沒有自己的時態與生命週期，
> 它完全繼承產出類別的，所以用**前綴**而不是新類別。

### 1.1 SPEC

- 檔名：`*_CORE_SPEC.md`、`<feature>-spec.md`

#### 狀態詞彙依 SPEC 子型分開（**不是一套套用到底**）

| SPEC 子型 | 狀態詞彙 | 理由 |
|---|---|---|
| **CORE SPEC**<br>**CONTRACT SPEC** | `權威` / `已取代`（兩態） | 橫切契約沒有「實作進度」。「時間單位是什麼」不存在 `Design Accepted` 這個狀態——它要嘛是現行權威，要嘛已被取代 |
| **FEATURE SPEC** | `Draft` → `Design Accepted` → `實作 Approved` → `已落地`（四態） | 功能有落地進度，而且進度本身是 agent 需要知道的事 |

**實跑證據：** 把四態硬套在橫切契約上的後果是——某專案 5 份 CORE SPEC
全部掛在「缺狀態標頭」warning 裡，而且沒人補得出有意義的值。
**永遠無法清零的 warning 會讓人停止看 warning**，那比沒有檢查更糟。

**已知缺口（未修）：** 另外兩類（DOMAIN-INDEX / PROCESS-RECORD）的狀態詞彙
尚未定義（**ACC 見 §1.7**；**REQ / DESIGN 見 §1.9**；
**TICKET 見 `control-flow.md` §1.1**）。
根因是每一版只針對該次實跑或該批產出撞到的類別收斂——
這兩類還沒有需求逼出詞彙。
影響範圍：這兩類目前只能寫自由文字，機械檢查 C10 對它們無法判定。
暫以各類別的時態規則（§1 總表）覆蓋——DOMAIN-INDEX 只寫現況、
PROCESS-RECORD 一律 SUPERSEDED——所以缺的只是「可機械判讀的詞彙」，不是語意。
併入下一次會動到這兩類的實跑。

- **R1：正文只描述現況。** 不寫「未來會改成」、不寫「目前仍是」。
- **R3：一個概念只有一個權威定義。** 判準見 §3。
- 被取代的內容**標記保留、指向現況**，不刪除（否則 agent 不知道那條路失敗過，會再走一次）。
- 已知缺口必須用固定形狀寫：
  ```
  **已知缺口（未修）：** <現象>。<根因>。<影響範圍>。<為什麼還沒修／併入哪一項>。
  ```
  理由：agent 讀到「已知缺口」會避開；讀不到就會以為那裡是好的。

### 1.2 ADR

- 檔名：`adr/NNNN-<slug>.md`，編號**永久保留、永不重用**
- **永不改寫，只追記。** 決定錯了就寫新的 ADR 標 `superseded_by`，舊的留原文。
- ADR 寫的是**為什麼**，不是**是什麼**。「是什麼」屬於 SPEC。
- 引用規則：可以寫「依 ADR-0012 的決定」，**不可以**寫「依 ADR-0012，現在的行為是 X」——
  ADR 不保證它描述的行為還活著，SPEC 才保證。
- 狀態詞彙（三態）：`Draft` → `Accepted` → `Superseded`。
  `Accepted` 只綁 human 核可該票 ACC（`acceptance` 關卡），
  由該票的 doc-sync 於核可後翻狀態列並附核可紀錄（日期、commit）；
  `Superseded` 於新 ADR `Accepted` 時由新 ADR 所屬票的 doc-sync 翻舊檔狀態列
  並寫 `superseded_by`（即上文「標 `superseded_by`」）。
  狀態列是檔頭唯一可改寫的行（檔頭表示法的遷移不算改寫）；正文自 `Accepted` 起只追記

### 1.3 DOMAIN-INDEX

- 檔名：`domains/<domain_id>.md` + 機械登記表 `domains.yaml`
- 唯一職責：**路由。** 給定一個領域或一個檔案路徑，指出哪份 SPEC 管它、有哪些 ADR、有哪些未結票。
- **這是唯一正當的「agent 專用」文件。** 理由見 §4。

#### 權威清單必須分型且有序

登記表的權威欄位**不得是無序平列**：

```yaml
<domain_id>:
  spec: docs/.../X_CORE_SPEC.md     # 恰好一份。唯一實作依據
  adr:                              # 決策，可多份，不保證描述現況
    - adr/0003-<slug>.md
    - adr/0007-<slug>.md
  process_record:                   # 不列入權威，僅供歷史查閱
    - docs/architecture/....md
```

機械檢查：

| 條件 | 等級 |
|---|---|
| `spec` 不是恰好一份 | **擋** |
| `spec` 指向的文件宣告類別不是 SPEC | **擋** |
| 清單內任一文件已被其他文件宣告 deprecated / superseded | **擋** |
| `process_record` 的文件被當作實作依據引用 | **擋** |

**實跑證據（這是壓測找到最嚴重的一項）：** 某領域的平列 `docs:` 欄位同時列出
——兩份各自自稱「唯一權威」「衝突時以本文件為準」的文件，
加一份已被其中之一宣告 deprecated 但**自身沒有 SUPERSEDED 標頭**的文件。
agent 查這個領域會拿到三個互相矛盾的答案，而且沒有排序或裁決規則。
既有的符號級重複權威檢查抓不到它，因為衝突發生在**文件級的權威宣告**，
不在 backtick 符號上。

### 1.4 PROCESS-RECORD

- 檔名：`architecture/`、`planning/` 下的規劃書與討論紀錄
- **可以**保留與現況不符的內容——它記的就是當時的想法
- **必須**在檔頭標 `SUPERSEDED` 或 `PROCESS RECORD`，並指向現況文件
- **不得**被引為實作依據。任何 agent 讀到這類檔案必須當成歷史，不是規格

### 1.5 TICKET

**必須存在兩型**（這是 L1）：

| 型 | 內容 | 來源 |
|---|---|---|
| **文件缺口型** | 有程式、但缺單一權威規格 | `inventory` 階段盤點 |
| **工程缺口型** | 功能缺陷、技術債、新功能 | `intake` 階段 |

**票號前綴屬於 L2,不是 L1。** L1 只規定 ID 的形狀與語意：

- 形狀 `<prefix>-<n>`，前綴由各專案自訂
- 專案內**全域唯一、永不重用**
- 結案後保留

> **實跑證據：** v0.1.0 把前綴寫成 `BL-DOC-n` / `BL-ENG-n`。
> 受測專案的 backlog 是單一型 `B1..B44`（現存 36 張）。
> 採用公版若要求換前綴，等於要重編 36 張既有票的號——
> 而「ID 永不重用」正是公版自己的規則。
> 判準我自己寫過：「這條規則換到另一個專案還成立嗎？」
> `BL-DOC` 這個字串換過去就不成立，所以它是 L2。

#### 票庫結構：一張票一個目錄，兩個檔

**L1 規定形狀**（下列三條換到任何專案都成立）：

```
<票庫>/<ID>/
  ticket.md     類別: TICKET   缺口描述與驗收意圖。開票後不改寫，結案時追記結果
  state.yaml    類別: TICKET   交棒檔：state / stage / depth / assignee / read_first
```

交棒檔的欄位正本在 `context-budget.md` §2（本節不重述）。
它是 YAML，類別宣告寫成註解——規則見 §1.0 的「非 markdown 文件」。

1. **票必須可被票號單一定址**——`<票庫>/<ID>/` 是該票的唯一主位置（C25 靠這條才跑得動）
2. **一張票 = 一個目錄**，不得單檔塞多張票
3. **票的狀態只寫在交棒檔**，`ticket.md` 不得有狀態欄位（C30）

#### 票目錄內可選 artifact 的位置與類別（DW-8）

強制兩檔之外，票目錄可有下列**可選** artifact。它們歸 **PROCESS-RECORD**
（§1.4：記「某次當時怎麼判／怎麼問」、凍結、不得引為實作依據），**不新增第十類**：

| artifact | 票內位置 | 類別 |
|---|---|---|
| 需求 | `<票庫>/<ID>/requirements.md`（REQ，§1.8） | REQ |
| 設計 | `<票庫>/<ID>/design.md`（DESIGN，§1.9） | DESIGN |
| 審查結論 | `<票庫>/<ID>/review-<stage>.md`（一受審關卡一檔；`<stage>` = `req`／`design`／`mechanical`／`domain`／`security`） | PROCESS-RECORD |
| 子代理回報 | `<票庫>/<ID>/report-<role>-<YYYY-MM-DD>.md`，或併入對應 `review-<stage>.md`（子代理作某關卡 reviewer 時其回報即該關卡審查結論） | PROCESS-RECORD |

審查結論有了票目錄內固定位置，`review` 階段（`stage-table.md` §1）的離開條件
「每個發現都有結論」才有 durable 落點（§0「無 durable artifact 的 gate 不是 gate」），
`control-flow.md` §2.4 的回報鏈壓縮才有處可查。

**給位置不等於給寫入權。** reviewer 無寫入權（`roles/_common.md` §7，不被推翻）；
子代理回報的落檔由委派該子代理的 **orchestrator 代存**，或由該票 **doc-sync** 於後續階段歸檔。

**`_common.md` §5 的「回報全文 ≤ 50 行」上限指「交 orchestrator 的摘要」，非落檔全文。**
約束的是傳給上游的摘要（回報鏈不被長文淹沒）；落檔的完整審查結論（PROCESS-RECORD）
是 durable 證據，長度由審查內容決定，不受此上限約束；此界定不放寬 §5 的上限。

**「子代理回報是否必須落檔」是否為新義務，歸 `DW-30`**（durable 簽核紀錄機制）——
本節只定「若落檔，放哪、由誰存、上限指摘要」三塊形狀，不把落檔成文定為新義務。

**L2 決定**：票庫路徑、票號前綴（§1.5 開頭）。

> **為什麼「一票一目錄」是 L1，不是品味問題。**
>
> 單檔多票的檔案只能增長——因為 §1.5 要求結案保留。
> 於是唯一能縮短它的手段就是**刪掉已結案的票**，
> 而那正是 `control-flow.md` §1.5 實測到的那條規則（「做完一項就從這裡刪除」）
> 及其後果（8 個票號懸空，每個仍被 1–4 份文件引用）。
>
> **刪票不是壞習慣，是單檔多票的必然結果。**
> C14 與 C25 擋得住那個動作，擋不住產生那個動作的壓力——只有結構能。
> 一票一目錄讓「永久保留」不花任何人的閱讀成本。

#### `ticket.md` 的固定欄位

`領域 / 現況 / 影響 / 要做 / 範圍 / 權威文件 / assignee / depends_on`

**狀態不在這張清單裡，這是刻意的。** 票的描述是「哪裡有缺口」——
開票時為真，結案後仍然為真；狀態是「現在誰該動」，每次轉移都變。
兩者時態不同（前者凍結、後者就地改寫），
**放同一個檔案就必須就地改寫一份本來不該改寫的東西**。
兩處都寫 → 擋（C30），理由是 R3：改狀態時只會改到其中一邊。

**`depends_on` 的正本在 `ticket.md`，`state.yaml` 為機械可讀副本（DW-7）。** 它是「哪裡有缺口、依賴什麼」
的描述，開票時為真、凍結於開票後；`state.yaml` 的 `depends_on` 是交棒用的現況副本，供 C 系列與狀態轉移指令讀。
**開票後才發現的依賴**：因 `ticket.md` 凍結不就地改，新增依賴記在 `state.yaml` 的 `depends_on`，並於交棒檔 log
註一行指明「`ticket.md` 票面未列此依賴、以 `state.yaml` 為準」。

**`ticket.md` 凍結後票面過時怎麼交代（DW-7）。** 票面欄位過時、開票即寫錯、或用集合詞而未列舉時，因 `ticket.md`
凍結不就地改，而在該票 `state.yaml` 的 log 一行交代「票面某欄已過時／寫錯，以 <現況出處> 為準」；判讀由 orchestrator
確認（票的改寫權屬 orchestrator，見本節總表 TICKET 列）。最終形狀對齊 `DW-8` 的 REQ 模板（若其定「票面與現況出入」一節，
則與本處並存：log 指路、REQ 節詳列）。

#### 硬規則：開票時不得現場編規格

這條不能只是口號，要有落地界線。**「要做」欄位限定寫方向與範圍**，
明文禁止以下內容——它們是契約條文，屬於後續 `design` 階段：

- 具體數值與閾值
- 欄位定義與資料型別
- 狀態機與轉移規則
- API 形狀（路徑、參數、回傳結構）

違反的處理：該票退回 `inventory`，內容移進 `design`。

理由：盤點的人手上沒有完整上下文（他正在盤 20 個領域），
現場編出來的規格會變成**假權威**——而且因為它寫在票裡，
看起來像是已經決定過的事。

#### 狀態詞彙與轉移

八態（`backlog` / `speccing` / `awaiting_human(gate)` / `ready` / `active` /
`blocked` / `closed` / `killed`）與轉移規則在
**`control-flow.md` §1**（正本，本節不重述）。

TICKET 的狀態詞彙放在控制流而非本檔的理由：它不只是標籤，
**每個狀態都綁一個「下一步由誰做」**——那是控制流的問題，不是文件分類的問題。
（其他類別的狀態只描述文件自身的生命週期，所以留在本檔。）

#### TASK 檔的形狀與位置（DW-7）

TASK 屬 TICKET 類，**不新增第十類**（§1.9）；差別只在粒度（TASK 擁 DoD、TICKET 擁 ACC，`stage-table.md` §7）。

- **位置**：TASK 承載於交棒檔 `state.yaml` 的頂層 `tasks:` 區塊，每個 TASK 一個 list item。本處不另立
  `tasks.md` 檔（其最終檔名歸 `DW-8`）；`tasks:` 區塊是否外移交棒檔歸 `DW-32`。
- **欄位**：`id` / `summary` / `assignee` / `depends_on` / `status` / `commit` / `covers` / `read_first`。
- **狀態值（三值）**：`todo`（未開工）/ `agent_done`（agent 做完、尚待 human 判或結案時翻 `done`）/ `done`（完成）。
  `blocked` 不入 TASK status——task 被擋以 `depends_on` 未完成表達，票級 `blocked`（`control-flow.md` §1.1、C21）另有欄，兩者不混。
- **`commit` 欄的回填**：task 做完提交時該筆 sha 在提交當下才存在，故 `commit` 欄於**下一筆** commit 回填
  （不採「由 git 主旨導出」——`check` 路徑不呼叫 git，且主旨與 task 的對應不保證唯一）。
- **次序**：由 `depends_on`（小 DAG）表達，不由 list 物理順序表達。次序改動（加／刪依賴、插入 task）記在交棒檔
  **log 一行**，不就地改寫已 `done` task 的 `depends_on`；新增 task append 到 `tasks:` 末尾、以 `depends_on` 接入 DAG。
- **gate 落點**：`awaiting_human` 的 gate 參數寫成頂層 `state:` 的值直接帶括號（`state: awaiting_human(acceptance)`），
  不新增獨立 `gate:` 頂層欄；與 C24 既有認法（`state: awaiting_human` 加 `gate:` 鍵、或括號形）一致。
- **`speccing`／L0 的 stage**：`speccing` 內 stage 隨主責角色在 `requirement`／`design` 間移動（analyst→architect）；
  `awaiting_human(spec_approval)` 的 stage 保持進入關卡前的階段；L0 直通（`backlog`→`ready`）的 stage 設為 `implement`
  前的待工（`stage-table.md` §6 L0 走 1→7→8→9），僅 `depth: L0` 時允許該轉移。

未定（不越界）：TASK 的 DoD 內容規範（planning 階段每票各寫）、`tasks.md` 最終檔名（`DW-8`）、tasks 外移（`DW-32`）。

#### 其他

- **結案後保留，標 `closed` + 結果。不刪除。**
  刪除已結案的票等於銷毀「這件事做過了」的證據，下次會重開一張一樣的。
  **實測後果見 `control-flow.md` §1.5**：某專案刪掉 8 張結案票，
  而那 8 個票號仍被 1–4 份其他文件引用——下一條因此同時被破。
- 方向性：SPEC 與 ADR **引用**票號（「本節解決 `<prefix>-7`」），
  票也指回文件。雙向連結是強制的。

### 1.6 LOG

- 檔名：`CHANGELOG.md`、`decisions.log`、`history.yaml`
- **只能 append。既有條目永不改寫、永不重排。**
- 與 PROCESS-RECORD 的差別：PROCESS-RECORD 是**一份凍結的文件**（會整份過時）；
  LOG 是**一串永遠為真的條目**（每條都綁一個時間點，所以永遠不會過時）。
- 與 SPEC 的差別：LOG 說「2026-10-05 決定了 X」，SPEC 說「現在是 X」。
  **X 後來被改掉時，LOG 那條仍然為真，SPEC 那句就是假的了。**
- 不可引為實作依據——「曾經決定過」不等於「現在仍然如此」。

> **這一類是 dogfooding 自我檢查撞出來的：** 本 repo 的 `CHANGELOG.md`
> 套不進原本的六類。它不是 SPEC（不描述現況契約）、不是 ADR（不是單一決策）、
> 也不是 PROCESS-RECORD（它永遠不過時）。
> 既有專案的 `decisions.log`、devrule 的 `history.yaml` 都屬於這一類。
> **六類不足以覆蓋實際存在的文件,所以加第七類**——
> 而不是把 LOG 硬塞進 PROCESS-RECORD。

### 1.7 ACC（驗收契約）

- 檔名：`acc/ACC-NNN.md`。模板：`templates/ACC.md`
- 在 `implement` **開始之前**由 verifier 與 human 共同定案
- **綁 DESIGN 的 normalized SHA-256**（全流程唯一的 hash 綁定，規則見 `stage-table.md` §8）
- **未經 human 核可的 ACC 只是 Draft，不是 ACC。** `implement` 不得開始

#### 狀態詞彙（四態）

```
Draft → 已定案 → 已驗 → 已取代
         ↑                  ↑
   human 核可，凍結      修訂後（§1.7 修訂路徑）
```

#### 輸入有三源，不是一源

| 來源 | 提供什麼 |
|---|---|
| 票的驗收意圖 | **「不能壞什麼」** |
| REQ 的驗收意圖 | 需求層的通過定義 |
| DESIGN | 「要做什麼」 |

每條 ACC 項**必填 `來源`**，且須通過**覆蓋檢查**：
票與 REQ 的每條驗收意圖至少對應一條 ACC 項。

> **ACC 由 verifier 提案，不是 architect。** architect 是 DESIGN 的生產者；
> 生產者定義自己的通過條件，就是「實作者解釋他做了什麼」的同一個失敗，
> 只是早了兩個階段。architect 對 ACC 的正當貢獻是**輸入**，不是 artifact。
> （v0.3.1 修正：本表原寫「architect 提案」，與 `stage-table.md` 第 5 列的
> 「verifier + human」矛盾。寫角色定義時撞到。）

> **實跑證據：** 某張 CSRF 票的 7 條驗收意圖裡，最重要的兩條是
> 「不得擋掉上游專案的既有呼叫」——而它們**不在 DESIGN 裡**。
> **DESIGN 寫「要做什麼」，不寫「不能壞什麼」。**
> verifier 若只從 DESIGN 推導驗收項，會寫出一份看起來很完整、
> 卻漏掉整張票最大風險的 ACC。

#### 驗收項分三型，型別決定必填欄位

| 型別 | 意思 | 額外必填 | 為什麼 |
|---|---|---|---|
| `NEW` | 新行為必須成立 | — | |
| `REGRESSION` | 既有行為**不得改變** | **基線證據**（`implement` 前取得） | 「它現在可用」無法與「它一直可用」「它本來就壞」區分 |
| `NEGATIVE` | 某件事必須**做不到** | **對照組**（同一測試在修正前必須失敗） | 負向斷言無法自證有效 |

> **負向斷言為什麼一定要對照組：** 一個回 403 的測試，可能是修正生效，
> 也可能是測試打錯端點、少帶 cookie、URL 拼錯——
> **兩者的輸出都是「不是 200」。**

#### 每條驗收項的欄位

`來源 / 條件 / 怎麼驗 / 證據放哪 / 判定方式 / 通過門檻 / 環境 / 驗證者 / 允許 SKIP`
（+ 依型別的 `基線證據` 或 `對照組`）

- **`判定方式`**：`二元` 或 `量化`。量化才需要
  `閾值 / 容差 / 量測次數 / 取值（最差 or 中位）`。
  二元項若硬填容差只會寫出廢話
- **`驗證者`**：`agent` 或 `human`。`human` 的項數 = 這張票要花掉你幾次實機操作，
  **定案時就看得見**（這是 `stage-table.md` §6.1 的關卡預算）
- **`允許 SKIP`**：`否` 或明確條件 + **殘留風險由誰承擔**。
  **所有 SKIP 必須在定案時授權**，`verify` 不得新增未授權的 SKIP

#### 環境矩陣必須指向可機械列舉的來源

一條驗收項 × N 個環境 = **N 格證據**，各自獨立標 PASS / FAIL / SKIP。

環境清單**不得在 ACC 裡抄一份**，必須指向設定檔（compose 的 entrypoints、
ingress、環境矩陣檔）——抄的那份會漂。

> **實跑證據：** 票裡散文寫「兩個入口」，部署設定實際宣告**三個**。
> 漏掉的那一個，正是票裡寫明的最大回歸風險唯一會被行使的環境。

#### 外部前提必須是可執行斷言

驗收通過所依賴、但**本專案不控制**的事實：
每條必填 `前提 / 版本或來源 / 怎麼重驗`。

> **實跑證據：** 某票的驗收依賴「某測試框架的 API client 不帶 `Origin` header」，
> 票裡寫了版本號 1.57。查 lockfile，resolved 版本是 **1.60.0**。
> 前提是在舊版實測的，現在跑新版，**而且沒有任何東西會報這件事**。
> 散文前提會無聲漂走；可執行的前提斷言不會。

#### 修訂路徑（凍結不等於不可改）

ACC 定案後凍結。修訂 = **開新版**，舊版保留原文並標 `superseded_by`，
**human 重新核可**。正當理由只有三類：

`DESIGN 變更` / `門檻不可達` / `驗證方式無效`

> **「結果不如預期」不是正當理由。**
>
> 凍結而不給修訂路徑，結果不是「沒人改」，是**偷偷改到它會過**。
> 那是整套流程裡最便宜、也最毀滅性的一個動作——
> 它讓驗收失去意義，而且**不會報錯**（§0 的「第二種更貴」是同一個形狀）。

### 1.8 REQ（需求條目）

- 檔名：票目錄下的 `requirements.md`（票庫結構見 §1.5）。ID 形狀 `REQ-<n>`，票內唯一
- `requirement` 階段由 analyst 產出，**凍結於 DESIGN 定案**
- 每條必須**可驗證**——「使用者體驗要好」不是 REQ，「匯入 5000 筆在 30 秒內完成」是
- 狀態詞彙：`Draft` → `已定案` → `已取代`（三態，見 §1.9 的共用說明）
- 引用寫法兩種：所在檔可定位票時——檔在票目錄 `<票庫>/<ID>/` 下，或檔頭有 `票：` 欄——
  裸 ID（`REQ-<n>`）指所在票的 REQ；引用別張票的 REQ，或所在檔定位不了票，
  在 ID 前加票號與斜線，如 `<prefix>-7/REQ-1`。機械解析只認這兩種。
  前面緊接別張票的票號或其檔案路徑的裸 ID（兩者之間只有空白，行內程式碼的反引號不計），
  以及定位不了票的檔裡的裸 ID，不做機械解析，只供人讀；LOG 類文字的既有條目不回改（§1.6）

#### `implement` 不得引 REQ

這是 REQ 與 DESIGN 唯一但決定性的差別，也是它值得單獨成一類的理由。

> REQ 寫「要達成什麼」，它**刻意不含實作決定**。
> implementer 若直接讀 REQ，就必須自己把缺的決定補出來——
> 而那些決定本該由 architect 做、由 `reviewer(design)` 審、由 ACC 綁 hash。
> 補出來的東西三道全部繞過，**而且它看起來像在實作需求**。

與 `analyst.md` / `verifier.md` 的「不該讀實作細節」是同一條原則的反向：
**上游不得預先決定下游的事，下游不得跳過上游的產出自己決定。**

#### REQ 不是 SPEC

| | 寫的時候 | 說什麼 |
|---|---|---|
| **REQ** | 做之前 | 要**變成**什麼 |
| **SPEC** | `docsync` 階段，做完之後 | **現在**是什麼 |

同一件事會在 REQ 與 SPEC 各出現一次，**而且那不是重複**——
時態不同、讀者的動作不同。把 REQ 當 SPEC 就地改寫，會讓需求史消失；
把 SPEC 當 REQ 寫未來式，會讓 agent 照著還沒做的東西寫程式。

### 1.9 DESIGN（設計）

- 檔名：票目錄下的 `design.md`。ID 形狀 `DESIGN-<n>`
- `design` 階段由 architect 產出，**凍結於 ACC 定案**（ACC 綁它的 normalized SHA-256）
- **必須可定址**：定址單位、anchor 規則、正規化見 `stage-table.md` §8.1–8.2
- 寫「要做什麼」，**不寫「不能壞什麼」**——後者是 ACC 的 `REGRESSION` 型驗收項（§1.7）
- `DESIGN-<n>` 票內唯一；引用寫法與解析規則同 §1.8。
  ACC 綁的是 `design.md` 的 hash（`stage-table.md` §8），不是 ID

#### 定案與修訂

定案 = `reviewer(design)` 或 human 核可，**核可紀錄必須留存**（C29 檢查這一項）。
定案後的修訂**不是就地改寫**：走 §8.3 的重新核可（hash 不符時 ACC 重新核可，而非擋）。

#### 狀態詞彙：REQ 與 DESIGN 共用三態

```
Draft → 已定案 → 已取代
```

與 ACC 的四態（§1.7）差一態，而那一態的有無是推導出來的：

> **ACC 多一個 `已驗`，因為 ACC 是追溯鏈上唯一會被執行的 artifact。**
> REQ 與 DESIGN 被「照著做」，但它們本身沒有通過／失敗；
> ACC 每一條都會產生一格證據，所以「定案」與「驗過」是兩件不同的事。
>
> 三者的 `已取代` 都走同一條修訂路徑：**開新版 + 舊版標 `superseded_by` + 重新核可**，
> 不是就地改寫（§1.7 修訂路徑是正本）。

> **DESIGN 是九類裡唯一「未來時態」又「可引為實作依據」的類別。**
> 其他八類都不是這個組合：SPEC 與 ACC 可引但描述現況或完成條件；
> PROCESS-RECORD 同樣是當時的想法，但**明文禁止被引為依據**。
>
> 這個組合是 DESIGN 必須被 hash 綁定的根因——
> 一份「還沒成真、但所有人照它施工」的文件，
> 是整套流程裡唯一沒有現實可以對照的東西。

#### 為什麼 TASK 沒有自己的類別

TASK 屬 **TICKET 類**，不新增第十類。用本檔 §0 的三問檢驗：

| | TASK | TICKET |
|---|---|---|
| 時態 | 現況 + 完成後保留 | 現況 + 結案保留 |
| 可引為實作依據 | ❌ | ❌ |
| 誰可改 | orchestrator | orchestrator |

**三問全同 → 同一類。** 差別只在粒度（TASK 擁有 DoD，TICKET 擁有 ACC，
`stage-table.md` §7 已規定兩者不混），而粒度不是分類。

> 這條判準與 `control-flow.md` §1.0 的狀態合併判準是**同一條**：
> 幾個候選若對該類別的定義性問題答案全同，它們就是同一個。
> 分類法與狀態機各自獨立推導，收斂到同一條規則——那是它成立的旁證。

#### REQ 定案後修訂的關卡與 human 核可形式

REQ 定案後的修訂（開新版）與初次定案走**同一道關卡**：再經 reviewer(req) 審，L2 票另需 human 核可
（`stage-table.md` §1 第 3 列、§6.1）；human 核可的形式與初次定案一致（答覆承接 orchestrator 請核可
的訊息、記入該票 `state.yaml` log 與 REQ 修訂紀錄表的「核可」欄）；正當理由沿用本節的修訂觸發
（開新版 + `superseded_by` + 重新核可），不另立 ACC 式三類理由。

## 2. ADR 與 SPEC 的產出時機不同

這是最容易做錯的一處：

```
design  階段產出 ADR     ← 決定當下就寫，因為它記的是「當時為什麼」
verify  階段產出 證據
docsync 階段更新 SPEC    ← 現實改變後才寫，因為它記的是「現在是什麼」
```

### 2.1 「FEATURE SPEC 先寫」和 R1 不衝突——靠狀態標頭

> **適用範圍：FEATURE SPEC 專屬。** CORE SPEC / CONTRACT SPEC 用兩態詞彙（§1.1），
> 本節的推論對它們不成立——橫切契約沒有「實作進度」可言。

矛盾：commit 慣例要求文件先進第一個 commit（後續程式碼才有東西可引用），
但 R1 說 SPEC 只能描述現況——程式還沒寫，SPEC 描述的就是未來，那它在說謊。

解法是**狀態標頭**：

```
Draft → Design Accepted → 實作 Approved → 已落地
                                              ↑
                              只能在 verify 產出證據之後才准翻
```

SPEC 可以先存在，掛 `Design Accepted`；驗收通過才翻 `已落地`。

> **狀態標頭不是裝飾，它是讓 spec-first 與 R1 相容的那個機制。**

機械檢查點：**宣稱 `已落地` 但找不到對應證據 → 擋。**
只寫「已完成」而不說範圍，是最貴的錯誤——因為沒人會再去驗。

## 3. SPEC 的粒度

四種粒度，實務上夠用：

| 粒度 | 它管什麼 | 特性 |
|---|---|---|
| **CORE SPEC** | 橫切契約（時間單位、KPI 公式、ID 規則） | 所有功能都要遵守。改它影響全局，一律 L2 |
| **FEATURE SPEC** | 一個對使用者可見能力的契約 | 最常見 |
| **CONTRACT SPEC** | 兩個專案之間的介面 | **不屬於任何一邊**，變更流程特殊 |
| **ADR** | 結構性選擇 | 不是 SPEC，見 §1.2 |

### 3.1 子功能通常不該有自己的 SPEC

它是母功能 SPEC 裡的一節。否則 SPEC 會增殖，同一個定義出現在三處，
然後就破了 R3。

### 3.2 粒度判準

> **SPEC 的粒度 = 「有獨立權威的最小單位」。**
> 測試法：**這個數字改了要改幾個地方？答案必須是 1。**

消歧義規則：

> **一個領域可以有多份 SPEC，但一個概念只能有一份 SPEC。**

## 4. 人與 agent：一份文件，兩種要求

**不要寫兩份。** 兩份副本必然漂移，直接違反 R3。

但兩種讀者讀法確實不同：

| | 人 | agent |
|---|---|---|
| 讀法 | 跳著看、看圖、看脈絡 | 線性讀，**讀到什麼就當現況** |
| 不確定時 | 會問 | **會自己編** |
| 需要 | 為什麼這樣決定、權衡過程 | 精確路徑、符號名、明確的「這裡是壞的」 |
| 容忍 | 模糊語氣 | 零容忍 |

結論：**同一份文件，骨架服務 agent，正文服務人。**

| 寫作規則 | 其實是為了誰 |
|---|---|
| 狀態標頭用固定詞彙 | agent（可機械判讀） |
| 引用給**函式名**而非行號（行號會漂） | agent（找不到就會自己編） |
| 已知缺口用固定形狀 | agent（讀到會避開） |
| 數字要有來源 | 人（建立信任） |
| 決策段落不寫「應該」「建議」 | 兩者 |

### 4.1 唯一正當的 agent 專用 artifact：索引與路由

agent 要問的是「我改了這個檔案路徑，哪份 SPEC 管它？」
**人從來不會這樣問問題。**

所以 `domains.yaml` 這類登記表是正當的第二份檔案——它不是真相的副本，
它是真相的**索引**，而且可以機械檢查是否與真相漂移。

其他任何「給 agent 看的版本」都是第二份真相，禁止。

| C30 | 票的狀態同時出現在 `ticket.md` 與交棒檔 | **擋** | FG-20 |
| C31 | 票庫裡的票目錄缺 `ticket.md` 或 `state.yaml` | **擋** | FG-19 |
| C32 | 已定案（`已定案`／`Accepted`／`已驗`）的 artifact 正文含「待確認」「一併評估」「視情況」等未決字樣 | 警告 | DW-8 |

C6 與 C12 是實跑中才浮現的：

- **C6** — 作廢的宣告寫在**取代者**身上，被取代者自己乾淨無標記。
  agent 讀到被取代者不會知道它已作廢（它不會去讀取代者）。
  宣告必須雙向，否則等於沒宣告。
- **C12** — 沒有任何 SPEC 引用某個 ADR 的決定，意思是那個決定要嘛沒落地、
  要嘛落地了但沒寫進規格。兩種都是缺口，而單純的「孤兒文件」檢查
  看不出 ADR 孤兒的特殊性。

C15–C20 來自 `acceptance` 實跑。其中 **C18 是整張清單裡最重要的一條**——
它守的是「改 ACC 讓它通過」這個動作。那是唯一一個
**會讓前面所有檢查同時失效**的操作，而且它看起來像在修文件。

C19 刻意只警告不擋：擋的話人會改成不更新 DESIGN，
那正是這套流程要防的事（理由見 `stage-table.md` §8.3）。

**C28–C31 來自 v0.5.0 的控制流實跑**（`runs/2026-10-05-dw-control-flow/`）。
四條守的是同一件事的兩端：**追溯鏈的每一節都要有類別、有定案者、有唯一位置。**

- **C29 是 C18 的上游版本。** C18 擋「改 ACC 讓它通過」，
  C29 擋更便宜的做法：**ACC 照規矩綁 hash，但綁的是一份從未被核可的 DESIGN。**
  整條鏈的每個 hash 都對得上，而鏈的起點沒人簽過名。
- **C30 與 C31 的對象是票庫本身**，而票庫是 C21–C27 全部七條的輸入。
  票庫結構沒有檢查，等於那七條建在無人檢查的地基上。

**C32 是 DW-8 新增的只報告警告級檢查**（ADR-0001 §2.1 (c)「新增只報告的警告級檢查」為凍結期允許變更）。
它偵測已定案（`已定案`／`Accepted`／`已驗`）的 artifact 正文仍留「待確認」「一併評估」「視情況」等未決字樣——
定案後還留未決字樣，是「看起來定了、其實沒定」的來源。**必為警告級，不得定為擋級**
（擋級＝新關卡＝受凍結，須走 ADR-0001 §2.2 例外）。**哪些字樣、哪些類別適用、正則與腳本實作，歸 `DW-1`**
（C1–C31 機械檢查的實作票，判定邏輯記於 `dw/registry.py`）；本表只定「C32 入表、是警告級、歸 DW-1 實作」。

**已知缺口（未修）：** C9（R3 破裂）無法單靠文字比對偵測。
根因是「同一概念」需要語意判斷，不是字串比對。
實跑驗證了這一點：既有的符號級比對能抓到 6 個 backtick 符號的重複定義，
但抓不到文件級的權威宣告衝突（那要靠 C4–C6 的結構檢查，不是語意比對）。
影響範圍：C9 目前只能由 reviewer 在 `docsync` 階段人工確認。
併入後續的 `scripts/` 實作，暫以 C4–C6 的結構檢查 + 角色職責覆蓋。
