## 2. 角色：三角色是否比較單純？

### 2.1 提案

| 角色 | 定位（草案） |
|------|----------------|
| **IE engineer (`ie`)** | 建立／編輯 **產品、SKU、SKU 版本、工序**（在權限允許的廠區範圍內），**送審**；**不**做審核通過／駁回；**不**做廠區 CRUD（但介面上 **仍須可選／可見廠區**）；**可** 使用 **主數據（詞彙）管理**（見 §4 已決議）。 |
| **manager** | 在 IE 能力之上，增加 **審核通過、駁回**；**廠區 CRUD**；**使用者管理**（見 §4）；與 **admin** 在 **功能面上無差異**（使用者已確認）。 |
| **admin** | 與 **manager** 在 **功能上對齊**（含使用者管理）；若日後需區分「僅系統維運／刪庫級操作」，再另開 **系統層** 條款。 |

**拿掉 `senior_ie` 的優點：** 角色矩陣變短、UI 分支與測試組合減少、文件與 onboarding 較單純。  

**工程現況：** 初始 schema（`0001`）仍建立四值 enum；**migration `0012`** 將既有 `senior_ie` **改為 `ie`** 並 **`ALTER TYPE ... DROP VALUE 'senior_ie'`**；執行中 DB 與應用層為 **三角色**。舊版 Phase1 **規格書**若仍出現 `senior_ie`，以本文件與 **`0012`** 為準逐步對齊。

### 2.2 權限原則（已納入使用者回覆）

- **IE**：可建立內容並送審；**不可**審核通過／駁回；**不可** 廠區 CRUD；**可** 主數據（詞彙）CRUD。  
- **manager / admin**：可審核；**可** 廠區 CRUD；**可** 主數據；**可** 使用者管理（與「僅 admin」之舊假設不同，**已確認兩者皆可**）。  
- **廠區**：由 **manager / admin** 管理；IE 在建立產品／SKU／版本等流程中 **必須仍能選擇／顯示** 已指派之廠區（唯讀或選單，依畫面設計）。

## 3. 資訊架構（分頁／區塊）

以下對應先前討論的「五區塊」，順序可依導覽習慣微調；本節描述 **資訊歸屬**，不綁定最終側欄層級（可為頂層五項或分組）。

| 區塊 | 內容（摘要） |
|------|----------------|
| **① 廠區與產品** | 廠區列表與 CRUD（**manager／admin**）；產品列表與 CRUD。 |
| **② SKU** | SKU CRUD；SKU 版本（version）CRUD、狀態流轉（草稿／審核／發布等依現行模型）。 |
| **③ 工序** | 選擇 SKU version → 工序列表編輯；**拖曳排序**；**群組**（`group_id` + 群組命名與視覺區塊）；**預覽**以 **topology／流程圖** 呈現群組與連線，標示 **整張工單的第一個步驟**；點群組可展開細項。**計算語意**仍為 **有序步驟序列**（見 §5）。 |
| **④ 數據管理（主數據）** | 管理 MOST 相關可控詞彙與設定（物件、動作、自／至、**手勢（hand）** 等——**實際種類以資料模型為準**）；**IE 與 manager／admin 皆可依 §4**；列表需可見 **技術 id、對外編碼、BOM／料號**（見 §6、§1.1）。 |
| **⑤ 使用者管理** | **manager／admin**（已確認）；維持現行能力為原則。 |

### 3.1 IE 與 manager／admin：導覽與篩選（已決議 — 2026-04-19）

- **IE：** 僅需看見與 **工序／SKU 版本編輯** **直接相關** 的導覽子集（**不**以全系「五區塊」同等展開為預設）。登入後以 **版本／工序** 為主；深連結進入某 `versionId` 時，依 **user_sites** 等規則檢查權限，側欄 **維持 IE 子集**。  
- **manager／admin：** 維持 **多列表**（廠區、產品、SKU、版本、使用者等），以 **廠區／產品**（及其他約定篩選）**收斂**至要操作的資料；**預設**可優先「當前廠區」或最近使用，避免一次載入全庫。  
- **群組資料歸屬（與 §5 一致）：** **版面／流程群組**（名稱 + `group_id`）隸屬 **SKU version**（步驟之下、版本之上）；**不同 SKU version** 可有同名群組（如「組裝段」），但為 **不同列／不同 id**；複製版本時 **沿用語意與名稱、發新 id**（不共用跨 version 的群組主鍵）。

## 5. 工序產品語意（與 MOST 核心邏輯對齊）

### 5.1 已共識方向

- **儲存與計算的 canonical 形式**：**有序列表** 的步驟，每步可帶 **`group_id`**（同一群組多步驟僅為 **分類／版面**，不改變 **全域順序** 時的預設解讀）。  
- **「第一項」**：指 **整張工單（該 SKU version 之步驟序列）的第一個步驟**，用於 topology 與「從頭檢視」的起點。  
- **Topology／連線圖**：**視覺化與確認用**，讓使用者快速理解流程；**預設不引入 DAG 分支語意**，除非未來另開規格。  
- **對 MOST 核心**：現行 **線性加總 TMU／工時** 的演算法仍以 **步驟順序** 為準；群組與圖 **不應** 在未定義規則下改變 index sum。

### 5.2 第一期 topology 範圍（使用者回覆）

- **僅線性 + 群組框** 作為 **第一期可交付範圍** —— **足夠**。  
- **要求**：**邏輯與實作必須正確**（排序、群組歸屬、與 TMU 計算一致），不因視覺簡化而產生錯序或重複計算。

### 5.3 實作含義（架構層）

- **排序**：需有穩定欄位（例如 `sort_order` 或陣列序），拖曳即更新該序。  
- **群組**：需有 **`group_id` + 群組列（含持久化 `name`）**；群組 **顯示順序** 可由「該群組內第一步的整體序」推導，或另存 `group_order`（細部 DDL 見專篇）。  
- **Topology 資料**：可由 **步驟 + 群組 + 整體順序** 衍生；若僅為 **單線 + 群組包裝**，圖演算法可保持簡單（例如群組當 compound node）。

### 5.4 與「之前版本」的關係

早期或原型中的 **主數據** 可能以 **前端靜態／無正式庫表** 維護；**目前 ddm-v2 已將詞彙等納入 PostgreSQL**（例如 `work_vocab_items`），並可由後台 API 維護。工序本身仍以 **版本化步驟** 為核心，與本節語意一致時，**不會** 因「多一層圖」而自動改變 MOST 公式 —— **圖是表現層**。

### 5.5 Topology：分層檢視與同步（已決議 — 2026-04-19）

- **第一層（使用者第一眼）：** **群組與群組之間** 的順序，例如 **群組 A → 群組 B**（線性，無 DAG 分支，與 §5.1 一致）。  
- **第二層（鑽入某群組）：** 該群組內 **步驟 1 → 2 → 3**（仍為 **同一條全域線性序** 的片段）。  
- **資料來源唯一：** **列表／表單** 與 **topology** 必讀寫 **同一套** `sort_order`、**群組定義**；**務必同步**；第一期 **topology 可唯讀**（由列表拖曳／編輯驅動），**圖上拖曳** 列為 **後續階段**（若實作，仍只允許回寫同一套欄位，不得另存「圖專用序」）。

### 5.6 版面群組 vs SIMO 組（已決議 — 2026-04-19）

兩者 **分欄、分標籤**，避免混淆：

| 概念 | 用途 | 與本文件用語 |
|------|------|----------------|
| **流程／版面群組**（建議 UI 標籤：**流程群組**） | **教學／視覺分區**；持久化 **名稱** + **`group_id`**；**不** 改變線性 TMU 加總規則（除非另定）。 | 即 §3、§5.3 之 **群組**。 |
| **SIMO 組**（既有 **`simo_group_id`**） | **時間計算**：同組內平行步驟只取 **max(step_tmu)** 再參與加總（見 `most_calculation_service`）。 | **不可** 與版面群組共用同一欄位。 |

### 5.7 群組資料範圍與線性約束（已決議 — 2026-04-19）

- **範圍：** 群組定義隸屬 **SKU version**（步驟所屬之版本）；**不同 version** 可有相同 **顯示名稱**、**不同群組 id 與內容**。  
- **線性：** **不允許**「步驟在群組之間交錯」的排序（例如 1∈A、2∈B、3∈A）；工序維持 **單一線性序**，群組僅為 **連續區段** 的切分與命名。

### 5.8 手勢與步驟 JSON（已決議 — 2026-04-19）

- **權威來源：** **`work_vocab_items`**（`kind = hand`）與全系 **`external_code`／UUID** 策略（見專篇 §5～§8）。  
- **步驟 JSON：** **不** 存顯示字串；存 **唯一識別**（**UUID 或 `external_code`**，與 API／專篇「工序步驟 schema」一致）。  
- **正式環境：** **不** 保留「legacy 字串／預設 Right」作為生效路徑；舊資料以 **migration／一次性對應** 收斂至主數據列，對應失敗者依營運規則 **阻擋或列管**（工程實作時另訂）。

## 6. 主數據、「global id」、對外編碼與匯出

**詳細作法（含問題說明、UUID vs 對外編碼、全系統唯一性三策略、中央登錄表 DDL、前綴登錄、BOM／料號預留、JSONB／EAV、匯入 staging、匯出 JSON 範例）已拆至專篇：**

- **技術鍵** 用 **UUID**；**對外** 用 **`external_code`（前綴分流，全系統唯一）**，必要時以 **中央登錄表** 保證 DB 層唯一（見專篇 §5）。

### 6.1 數據管理 UI（④）建議最低欄位

列表除名稱外，至少顯示：

- **技術主鍵**：`id`（UUID）  
- **對外編碼**：`external_code`（或約定後之 **`export_key`**）  
- **BOM／料號**（若 schema 已定義且適用該列）  
- **種類／範圍**：`kind`、`site_id`（或「全域」）  
- **狀態**：`is_active`

|------|------|
| **admin vs manager（功能）** | **無差異**；**manager 也可做使用者管理**。 |
| **IE／廠區** | IE **不可** 廠區 CRUD；**仍須** 在介面上選擇／顯示廠區。 |
| **IE／主數據** | IE **可以** 管理主數據（與 manager／admin 相同能力）。 |
| **topology 第一期** | **線性 + 群組框** 足夠；**邏輯與實作必須正確**；**topology 唯讀同步**、圖上拖曳 **後續**（§5.5）。 |
| **流程群組 vs SIMO** | **分欄、分 UI 標籤**（§5.6）。 |
| **群組範圍** | **SKU version** 下之群組列；**不同 version** 同名不同 id（§5.7）。 |
| **手勢／步驟 JSON** | **主數據權威**；JSON **僅存識別碼**；**無** 正式環境 legacy 字串路徑（§5.8）。 |
| **對外編碼與唯一性** | 需 **`external_code`（或同等）全系統唯一**（含 sequence model 等）；建議可讀前綴如 **`OBJ0001`**；並需 **BOM／料號**（或類似）欄位；**所有編號類欄位 unique**。 |
| **彈性屬性** | 建議評估 **EAV** 與 **JSONB**（見 §9.3）。 |
