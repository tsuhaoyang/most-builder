# 階段主表 (Stage Table)

## 0. 命名原則

兩條，決定了這張表為什麼長這樣：

1. **階段按「產出什麼」命名**，不按動作命名。
   所以沒有 `design` 和 `architect` 兩個階段——它們產出同一類 artifact。
2. **關卡按「誰核可」命名**，不按「做了什麼檢查」命名。
   這樣才看得出人工成本落在哪裡。

推論：**一個 gate 如果沒有產出 durable artifact，它就不是真的 gate。**
（這條同時是 context 清理點的定義，見 `context-budget.md`。）

## 1. 主表

深度欄位：`✔` 必走、`△` 條件性、`—` 不走。深度定義見 §6。

| # | stage | 主責角色 | 產出（文件類別） | 進入條件 | 離開條件 | 關卡核可者 | L0 | L1 | L2 |
|---|---|---|---|---|---|---|:--:|:--:|:--:|
| 1 | `intake` | orchestrator | TICKET 或 kill 紀錄 | 有一個請求 | 已與既有票／SPEC 比對；已分類為 new / revision / 已涵蓋 / kill | ✅ **human**（做不做） | ✔ | ✔ | ✔ |

| 3 | `requirement` | analyst | REQ 條目 | intake 判為 new / revision | 每條有 statement、驗收意圖、priority；無重複（重複折進既有條目） | reviewer(req)<br>**L2 才要 human** | — | ✔ | ✔ |

| 6 | `planning` | orchestrator | TICKET + TASK（含 `depends_on`） | ACC 已核可 | 每條 DESIGN 對應到至少一個 task；每個 task 的 `read_first` ≤ 4 個檔案 | — | — | ✔ | ✔ |
| 7 | `implement` | implementer(by stack) | code + **一 task 一 commit** | task 為 `ready`（依賴全完成） | 本機驗證通過；commit 存在；task 完成紀錄已寫 | — | ✔ | ✔ | ✔ |
| 8 | `review` | reviewer(mechanical)<br>+ reviewer(domain)<br>+ reviewer(security)<br>（對外服務必走） | 審查結論 | 有 diff | 每個發現都有結論：修掉／記為已知缺口／誤報並附證據 | 涉及邏輯變更 → ✅ **human 裁決** | ✔ | ✔ | ✔ |
| 9 | `verify` | verifier | 證據（ACC 指定位置） | review 無阻斷發現 | ACC 每條 × 每個環境格標 PASS / FAIL / SKIP；**不得新增 ACC 未授權的 SKIP** | ✅ **由 ACC 決定**<br>（ACC 中 `驗證者: human` 的項目需 human 判定） | ✔ | ✔ | ✔ |
| 10 | `docsync` | doc-sync | SPEC 更新 + 狀態翻 `已落地` + 決策紀錄追加；若本票發版，含根 README 版本列與 CHANGELOG 置頂條目（核可者＝本列的 docsync 核可）；L0 依本列深度欄 △：該票發版才走此步 | human 已核可邏輯變更 | 受影響的**所有**位置都已處理；R3 未破 | ✅ **human 核可後才動** | △ | ✔ | ✔ |
| 11 | `release` | implementer + human | 部署紀錄 + **部署後驗證證據**；annotated tag（核可者＝本列的上線決定；tag 的落點／時點／訊息見 DW-17）；L1 依本列深度欄 △：對外服務發版才走 | verify 全 PASS | 服務實際回應正確（不是「部署成功」）；回滾路徑已確認可用 | ✅ **human（對外服務必到）** | — | △ | ✔ |
| 12 | `observe` | orchestrator | incident 紀錄 → 新票 | 已上線 | 已完成四層分流（§3） | ① 止血決定 = ✅ **human** | ✔ | ✔ | ✔ |

**關鍵排序**：`acceptance`（第 5）在 `implement`（第 7）**之前**。兩個理由：

1. 驗收方式必須在寫程式前談定，否則驗收會退化成「實作者解釋他做了什麼」
2. **`REGRESSION` 型驗收項的基線證據只能在 `implement` 之前取得。**
   改完才想補拍已經來不及——「它現在可用」無法與「它一直可用」區分
   （實跑撞出的，見 §1.2）

**關鍵分工**：`design` 產出 ADR，`docsync` 更新 SPEC。
理由見 `doc-taxonomy.md` §2。

### 1.1 `inventory` 執行規範

舊專案納管的入口。它是整個流程裡**唯一會無界擴張**的階段，所以規範比別的階段細。

#### 第一步：`SCOPE` 先成文並核可（不可跳過）

一個成熟 repo 的「缺口」是無界的——可以一路盤到測試覆蓋、
程式與文件的語意一致性、每條 invariant 是否仍成立。
**沒有先定範圍，盤點不會終止**，而且兩次跑會得出不同結果，
於是無法判斷文件健康度有沒有改善。

`SCOPE` 必須寫出：

```
盤點對象：     <哪些領域 / 哪些目錄>
盤點項目：     <§1.1 判準表中的哪幾項>
明確不盤：     <項目 + 為什麼不盤 + 它屬於哪個階段>
預估票數上限：  <超過就停下來重新談範圍>
```

**`明確不盤` 是必填欄位。** 沒寫等於默認全盤。

#### 第二步：固定判準表（每項逐一標 PASS / GAP / N/A）

| # | 判準 | GAP 的意思 |
|---|---|---|
| I1 | 領域權威清單所列文件是否存在 | 斷鏈 |
| I2 | 權威清單的 `spec` 是否恰好一份 | R3 已破或無規格 |
| I3 | 所列文件是否都有 `類別:` 宣告 | 類別不明，agent 無法判斷能否引用 |
| I4 | 被引為實作依據的文件，類別是否為 SPEC | 把過程紀錄當規格 |
| I5 | 清單內是否含已 deprecated / superseded 的文件 | 指向作廢權威 |
| I6 | 狀態標頭是否存在且符合該 SPEC 子型的詞彙 | 無法判斷是否落地 |
| I7 | 程式碼是否都被某個領域覆蓋 | 無主程式 |

判準表是 L1，**不得臨場增刪**。要改就改公版（走 MAJOR / MINOR 升級）。
理由：判準不穩定 → 盤點結果不可比較。

#### 第三步：票批次核可

`inventory` 的產出是票，而票會消耗你之後的裁決預算。
一次盤點倒 40 張票進 backlog，等於無聲地花掉你未來幾週的關卡額度
——這與 §6.1「人工關卡是預算」直接衝突。

所以離場需要 human **批次核可**：「這批票成立、優先序如此、是否有要提前的」。
**一個決定，不是每張票一個決定。**

#### 硬規則：不得現場編規格

界線與違反處理見 `doc-taxonomy.md` §1.5。

### 1.2 `acceptance` 執行規範

全流程**唯一的必到人工關卡**。ACC 的欄位規範在 `doc-taxonomy.md` §1.7，
模板在 `templates/ACC.md`；本節只定階段層面的三條硬規則。

#### 進入條件：DESIGN 有未決項 → 擋

**尚未決定的設計不可能有驗收標準。**
DESIGN 裡任何「一併評估」「待確認」「視情況」都是阻擋項——
它決定了 ACC 要不要多一條驗收項、多一個環境格。

退回 `design` 補完，不要先寫一份有洞的 ACC
（有洞的 ACC 會在 `verify` 當天變成現場決定，那時沒有人會回頭找 human）。

#### 定案的三件事必須同時成立

| | 失守的後果 |
|---|---|
| **覆蓋檢查** 票／REQ 的每條驗收意圖都有對應 ACC 項 | 漏掉「不能壞什麼」——它不在 DESIGN 裡 |
| **基線已取得**（`REGRESSION` 型） | 進 `implement` 後就再也拍不到了 |
| **SKIP 已授權** 逐項標，含殘留風險承擔者 | SKIP 落到 `verify` 當場決定，等於實作者自己放過自己 |

#### SKIP 的授權時機是定案，不是 `verify`

「`SKIP` 誠實標記」是誠實的，但**太晚**。
`verify` 階段只能行使 ACC 已授權的 SKIP；
需要新增就是 **ACC 修訂**（`doc-taxonomy.md` §1.7），要回頭找 human。

> **實跑證據：** 某票有一條驗收項依賴 TLS 終結環境，而該環境在部署設定裡
> 有宣告、port 有 publish，但掛上去的 router 數是 **0**——這條必然 SKIP。
> 若留到 `verify` 當場決定，被放過的正好是票裡寫明的最大回歸風險。

## 2. 定期關卡（不屬於任何票）

時間觸發，不是事件觸發。它們沒有主人，所以永遠不會被做——除非明確排程。

| 關卡 | 頻率 | 產出 | 失敗處理 |
|---|---|---|---|
| 依賴安全稽核 | 每次 CI + nightly | 稽核報告 | **阻斷式**，不是警告 |
| 依賴鎖檔漂移 | 每次 CI | diff | 擋 |
| 憑證／網域到期 | 每月 | 到期清單 | 到期前 30 天自動開票 |
| 文件漂移盤點 | 每季 | `BL-DOC-*` 票 | 進 `inventory` |
| 備份可還原驗證 | 每季 | 還原證據 | 未驗證過的備份視為不存在 |

這些失敗一律**先開票**再處理，不在定期關卡裡現場修——
否則定期關卡會變成一個沒有盡頭的工作區。

## 3. incident / bug 四層分流

`observe` 階段的產出。**兩段必須分離**：

```
① 止血決定        assignee: human     ← 要不要 revert／關閉功能／降級
② 診斷與分級      assignee: analyst   ← agent 提案，跨級才升給 human
```

把兩段混在一起的後果：為了判斷「該不該 revert」而先做完根因分析，
期間服務持續壞著。**止血不需要知道根因。**

分級路由：

| 級 | 判準 | 路由 |
|---|---|---|
| **L-契約** | 違反 SPEC 或 invariant | → `requirement`，走全流程，L2 |
| **L-設計** | SPEC 對但設計沒覆蓋這個情境 | → `design`，L1/L2 |
| **L-實作** | 設計對但程式寫錯 | → `planning`，L0/L1 |
| **L-環境** | 程式對但環境／設定錯 | → `release`，不改程式 |

升級規則：agent 提出分級，**只有跨級時**才需要 human 裁決
（例如 agent 判 L-實作但 reviewer 認為是 L-契約）。

### 3.1 revert 是一等公民

`revert` 不是「一個普通的修改」：

- 止血 revert **可以跳過** `requirement` / `design` / `acceptance`
- 但**不可以跳過** `verify`（revert 完要驗服務真的好了）
- 且**必須**留下一張票記錄「為什麼 revert、什麼時候要修回來」，
  否則 revert 會變成無聲的功能消失

## 4. 特殊變更型態

### 4.1 migration 不是普通 task

資料遷移**不可逆**，所以它不走第 7 階段的一般規則：

- 必須 **expand / contract 兩段**：先加相容的新結構，切換，再移除舊結構。
  兩段是兩張票，中間必須經過一次 `release` + `verify`
- 必須明確寫出**部署順序**（先程式還是先 schema）
- 必須有**還原程序**，而且還原程序本身要被驗過
- 一律 **L2**（human 必到）

### 4.2 跨專案契約變更

CONTRACT SPEC 不屬於任何一邊，所以不能由任何一邊單方面改：

1. 提案方開票，票同時掛在兩個專案
2. **兩邊的 human 都核可**才進 `design`
3. 契約版本號遞增（不改舊版語意）
4. 明確寫出**上線順序**：消費方先容忍新舊兩版 → 生產方切換 → 消費方移除舊版支援
5. 一律 **L2**

**已知缺口（未修）：** 契約版本協商沒有機械檢查。
根因是兩個 repo 沒有共享的 CI。
影響範圍：順序寫錯會造成一邊上線後另一邊壞掉。
目前靠第 4 點的書面順序 + 兩邊 human 核可覆蓋，待日後補跨 repo 檢查。

## 5. WIP 限制與優先序

> **人工關卡是預算，不是免費的。**

7 個關卡 × 5 張平行票 = 35 個決定／輪。這種流程會被放棄，
不是因為它錯，是因為它貴。

規則：

- **WIP = 1 張票 / 1 個 session。** 平行票的 context 是相乘的（見 `context-budget.md`）
- **同時在飛的票上限 3 張**，而且不得有兩張同時卡在 human 關卡
- **不插隊。** 新票進 backlog 並評級，不打斷在飛的票。
  例外只有：止血（§3.1）與定期關卡的阻斷式失敗
- 評級與插隊是**兩個獨立決定**。「這張很重要」不等於「現在就做」

> **這兩條上限自 v0.4.0 起是可機械檢查的**，因為票有了狀態詞彙：
> `count(state == awaiting_human) ≤ 1`、
> `count(state in {speccing, ready, active}) ≤ 3`
> （`control-flow.md` §1.2 與 C24）。在那之前它們只是散文。

## 6. 深度階梯 L0 / L1 / L2

> L0／L1／L2 的差別，本質上就是**你本人要經過幾道關卡**。

| 深度 | 適用 | 走哪些階段 | human 關卡 |
|---|---|---|---|
| **L0** | 範圍小、風險低、不需 requirement／design 的改動（例：一行修、錯字、設定值、止血 revert）；**深度由 human 定**（§6.1「做不做」、`control-flow.md` §1.4），這四個例子為示意非窮舉——`DW-1` 第一批（八條機械檢查加測試）由 human 定為 L0 即此類 | 1 → 7 → 8 → 9（→ 10 若契約有變） | 1 道：做不做 |
| **L1** | 一般功能、子功能 | 全流程，但 requirement / design 由 reviewer 把關 | 3 道：做不做、ACC 定案、docsync 核可 |
| **L2** | CORE SPEC、架構變更、對外服務、migration、跨專案契約 | 全流程 | 5–6 道：加上 requirement 審、design PASS、上線決定 |

### 6.1 human 關卡預算

| 關卡 | 要不要你本人 | 理由 |
|---|---|---|
| ACC 定案 | ✅ **必到** | 「怎樣算做到了」只有你能定。這是全流程最便宜也最值得的一道 |
| 邏輯變更裁決 | ✅ **必到** | reviewer 發現語意漂移，是 bug 還是新決定，只有你知道 |
| 做不做 / kill | ✅ **必到** | kill 是一個正當結論，而且只有你能下 |
| 上線決定（對外服務） | ✅ **必到** | 不可逆 |
| bug 分級 | ⚠️ agent 提案 | 只有跨級才升 |
| design PASS | ⚠️ L2 only | L1 交給 reviewer(design) |
| requirement 審 | ⚠️ L2 only | L1 交給 reviewer(req) |
| task 切分 | ❌ 不要 | 這是 orchestrator 的工作，你插手只會變成瓶頸 |

**正常情況下一張 L1 票應該只花掉你 3 個決定。** 超過就是深度選錯了。

## 7. 追溯鏈與 ID

```
REQ-007 → DESIGN-011 → ACC-004 → TICKET-012 → TASK-045/046/047
                                                      ↓
                                        commit + 完成紀錄 + 證據
```

**鏈上每一節的文件類別、時態、可否引為實作依據：`doc-taxonomy.md` §1 總表。**
（REQ 與 DESIGN 的類別是 v0.5.0 才補的——
在那之前鏈上 5 節有 3 節無類別可宣告，見 `runs/2026-10-05-dw-control-flow/` FG-21。）

規則：

1. **TICKET 擁有 ACC**（驗收標準）；**TASK 擁有技術完成條件**（DoD）。兩者不混
2. 依賴只有兩層：**ticket 之間**、**同一張 ticket 內的 task 之間**。
   跨 ticket 的 task 依賴是**切分錯誤的味道**——該合票或該拆票
3. ticket 結案條件 = 所有 task 完成 **且** ACC 每條有證據。
   少一個就不是 closed。L0 直通路徑另計（§6 走 1→7→8→9，無 task、無 ACC）：
   結案依據為 `verify` 判定通過 **且** 文件同步完成（`control-flow.md` §1.1 `closed` 列）。
   L2 另計：`release` 對 L2 必走（§1 第 11 列 `✔`），對外服務的 L2 結案須含 release 的部署後
   驗證證據（`control-flow.md` §1.1 `closed` 列）；非對外服務的 L2 不觸發 release，退回「task＋ACC」一般結案
4. 所有 ID **永久保留、永不重用**，結案後仍保留；唯一性分兩層：
   **票號**全域唯一（`doc-taxonomy.md` §1.5）；
   **票內 artifact 的 ID**（`REQ-<n>`、`DESIGN-<n>`、`ACC-NNN`）票內唯一，
   跨票引用時在 ID 前加票號與斜線（如 `TICKET-012/DESIGN-011`），
   該組合全域唯一（`doc-taxonomy.md` §1.8、§1.9）；
   其餘 ID（含 `TASK-<n>`）全域唯一。
   ACC 的 ID 與 REQ、DESIGN 同層：TICKET 擁有 ACC（第 1 條），
   所屬票寫在 ACC 檔頭的 `票：` 欄（`templates/ACC.md`）
5. **雙向連結強制**：上游列出下游 ID，下游引用上游 ID
6. **ID 前綴屬於 L2。** L1 只規定形狀（`<prefix>-<n>`）與語意（§7 第 4 條）。
   公版不得要求既有專案換前綴——那會逼它重編既有票號，
   違反公版自己的「永不重用」規則。詳見 `doc-taxonomy.md` §1.5

### 7.1 assignee

預設 `assignee: <agent-role>`。以下情況必須 `assignee: human`：

- 裁決（邏輯變更、bug 跨級分級、契約爭議）
- 對外溝通
- 真機 / 實體環境驗證 ← 在 ACC 裡逐項以 `驗證者: human` 表達（§1.2）
- 上線與回滾決定
- kill 決定

> **本條與主表第 9 列曾經互相矛盾**（主表寫 `verify` 無 human 核可者，
> 本條卻要求真機驗證必須 human）。兩條矛盾的指令會讓 agent 行為不可預測。
> v0.3.0 修為：核可者由 ACC 逐項決定，主表不再寫固定值。

## 8. hash 綁定只有一處

**只有 ACC ↔ DESIGN 綁 SHA-256。**

不做全鏈綁定（REQ→SPEC→DESIGN→REVIEW 逐層 hash）。理由：
全鏈自動失效會產生持續的假失效，人就會開始不更新文件——
那正好是這整套流程要防的事。

綁 ACC ↔ DESIGN 的理由：設計變了而驗收標準沒跟著變，
是唯一會導致「驗過了但驗錯東西」的情況，而這種錯不會自己浮現。

### 8.1 hash 的單位是 artifact，不是檔案

DESIGN 必須**可定址**：獨立檔案，或 `檔案#anchor`，
且 **anchor 是標題，不是行號**（行號會漂）。

> **實跑證據：** 某票的 DESIGN 是一份 733 行、承載 36 張票的 backlog 檔裡
> 第 683–687 行的一個 619-byte bullet。
> 綁整檔 hash → **任何其他票的編輯都會改掉它**，每次假失效，
> 正好是本節自己說要避免的事。

### 8.2 正規化規則

沒有正規化，hash 不可重現；不可重現的 hash 不是檢查。

| 規則 | 理由 |
|---|---|
| 行尾統一 LF | 跨平台 |
| 去 trailing whitespace | 編輯器會自己動 |
| 壓平段內換行（連續空白 → 單一空格） | 為排版在句中硬斷行不是設計變更 |
| **排除標頭與狀態列** | 狀態會因階段推進而變，那不是設計變更 |

> **「標頭」的機械界線（DW-8／DESIGN-2）：** 檔頭遷移成 YAML frontmatter 後，
> **標頭 = 第一個獨立成行的 `---` 到第二個獨立成行的 `---` 的整個 frontmatter 區塊
> （含這兩行與其間所有欄位行），整段排除；hash 取第二個 `---` 之後的正文。**
> 取法 `awk 'f; /^---$/ && ++c==2 {f=1}'`——翻 `狀態:` 欄或增刪 frontmatter 欄位都不改 hash，
> 正是本列「排除標頭與狀態列」要的性質。此句只更精確定義「標頭」一詞，不改 §8「只綁 ACC↔DESIGN、
> 不做全鏈 hash」的綁定語意、不改 §8.3 警告不擋、不改 C19 等級。

> **實跑證據：** 同一段 DESIGN 原文 hash 與壓平空白後的 hash
> 是**兩個不同的值**。沒定義正規化，兩邊各算一次就不會相等。

### 8.3 hash 不符的處置不是「擋」

```
hash 不符 → verifier 逐條標示受影響的 ACC 項 → human 重新核可 → ACC 版本遞增
```

**擋會讓人改成不更新 DESIGN。** 所以這是警告級（`doc-taxonomy.md` C19），
但它觸發的流程是強制的：ACC 修訂必須回到 human，
且必須寫出**哪幾條 ACC 項受影響**——不能只說「已重新確認」。
