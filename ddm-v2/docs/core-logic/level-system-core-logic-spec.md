## 1. 定義與目的（教學檔案原文）

> **什麼是 Level System？**
> Level System 是一種**數位化組裝邏輯的表達方式**，目的是解決組裝過程中遇到的**順序問題**。過程中不會是單純的順序排列，要考慮**機型結構不同、自動化設備操作、治具操作**等情況。將這些邏輯數位化表達後，**系統才能對數據進行學習，並找到最佳的組裝流程**。

**概念框架（User 2026-06-16）：**
- **MOST** ＝把**工序標準化**，並切割到**細粒度的動作單元**。
- **Level System** ＝**限制工序**——把作業流程／動作粒度**邏輯化**，目的有二：①**讓 IE 填寫時不會出錯**；②**定義出標準化流程**供 LB 使用。

定位：介於 **MOST System（動作＋標準時間）** 與 **Line Balance（線平衡分站）** 之間的**邏輯層**；本身不算時間、不排站，只**定義排站規則**（先後、綁定、分割限制），交給 LB 演算法求最佳分站。

> **LB 是另一個獨立 project（User 自行開發中）。** 故本報告對 LB 只負責定義**輸出合約**（§9），不含 LB 內部演算法；ML「學習找最佳流程」願景**本期不做**（§13 Q8）。

```
[MOST System] --(動作清單 + 標準時間)--> [Level System] --(邏輯 → 圖/矩陣)--> [Line Balance 演算法] --> 最佳分站 + LBR + MI
```

## 2. 欄位模型（7 個參數，教學檔案原文）

教學檔案明列「主要參數有七點」，對應表格欄位如下：

| # | 參數（中文） | 對應欄 | 說明 |
|---|------|------|------|
| 1 | **動作描述** | 內容 / Content / MI | 該動作的標準描述，須經 **IE 審核**認定為標準描述才可用 |
| 2 | **動作時長** | Second | **= 原始秒數 × 系數（寬放係數）**。即 `Second = 標準時間 × 寬放係數` |
| 3 | **分割限制名稱** | Number | 限制「相同名稱動作」在同一站別的標籤；命名 `nb`+數字（例 `nb1`、`nb2`） |
| 4 | **分割限制數量** | Number_Count | 標籤的限制數量；**須為正整數** |
| 5 | **歸屬名稱** | Ascription | 群組歸屬的功能字符；命名「功能字符＋數字」；**名稱不可重複**；**main 不含在內**（例 `sub1`、`cub1`） |
| 6 | **歸屬層級** | Level | 該歸屬下的層級；**正整數**（亦可為**變動範圍**，見 §5） |
| 7 | **從屬名稱** | Countersignature | 此列所衍生／所屬的子群組標籤；命名「功能字符＋數字」；**名稱不可重複**；**main 不含**（例 `sub1`、`cub1`） |

> 輔助欄（圖中可見）：最右側還有一個 **群組內順序（depth order）** 欄，記錄某 sub/cub 群組內各列的先後（1、2、3…）。
> `Second` 公式驗證（image2）：`A` 原始秒數 5 × 系數 1 = Second 5。✓

## 3. 四種功能字符（功能字符 / Function Characters）

> 「字符的功能為表達不同種類的動作群組，目前現有 main、sub、cub、nb 這四種。」

| 字符 | 名稱 | 語意 | 放在哪一欄 |
|------|------|------|-----------|
| **main** | 主要順序分層 | 編輯層級中的**主要層級**；**所有層級文件的最初分層必須使用 main** | Ascription（最頂層） |
| **sub** | 次要順序分層 | **層級深度到 2 以後**所用的順序編制（可獨立排序、可在 main 約束下移動的群組） | Countersignature |
| **cub** | 次要固化分層 | 將動作**固化成系統無法分割的動作區塊**（同站、站內順序固定） | Countersignature |
| **nb** | 分割限制元素 | 限制**擁有相同元素標籤的層級數量**（每站最多幾列帶此標籤） | Number（＋Number_Count） |

關鍵原則：
- **main 不可作為「歸屬名稱／從屬名稱」**——main 只表達最頂層 precedence，不作為子群組標籤。
- sub、cub、nb 的編號**不可重複**（同一份 level 表內 `sub1` 只能定義一次）。

## 4. 深度階層（Depth）—— 本模型的核心

Level System 是**多層深度**結構，不是扁平欄位：

| 深度 | 字符 | 作用 |
|------|------|------|
| **深度 1** | **main** + Level 數字 | 全域 precedence 層；同一 Level 數字＝同一先後層（層內可並行／可互換／可分到不同站） |
| **深度 2** | **sub** | 在某個 main 層內，給一組動作**獨立的內部順序**；整組可在 main 約束下前/後移 |
| **深度 3** | **cub** | 把一組動作**固化為不可分割區塊**（同站、站內順序固定） |
| 橫切 | **nb** | 跨層的**每站數量上限**約束（不屬於深度階層，是獨立的資源/分割限制） |

**「延伸一個深度」的做法（教學原文）：** 要讓某子集（如 D、E、F）擁有獨立順序，就「將這幾個動作**向後延伸一個深度**」——在原 main 層級後新增一個附屬標籤（如 `sub1`），再把這些動作的**從屬（Countersignature）設成 `sub1`**，並用群組內順序欄排 1、2、3。

**Ascription / Level / Countersignature 三欄關係（由 image5 邊界圖確證）：**
- `Ascription` = 此列屬於哪個歸屬（最頂層為 `main`）。
- `Level` = 在該歸屬下的層級數字（可為 `3~4` 變動範圍）。
- `Countersignature` = 此列**衍生/帶出**的子群組標籤（`sub1`/`cub1`），其後續成員以群組內順序欄歸入。

## 5. 變動層級符號「~」（Jump / OR 邏輯）

> 教學原文：「依據動作要求 A 可以在此兩組動作間跳躍，因此我們這邊將用到**變動層級符號「~」**，將 A 動作的歸屬 main 層級設置成 **`1~2`** 即可。」

- `Level = "1~2"` 表示該動作**可在 main 層級 1 或 2 之間浮動/跳躍執行**（既可排在第 1 層、也可排在第 2 層，由 LB 取最佳）。
- image5 另見 `Level = "3~4"`。
- 對應需求清單第 3 點：**「『或』For main 1/3 — 動作可以在 1 或 3 被執行」**（注意：可能不限相鄰，`1/3` 暗示也支援非連續，待確認語法是 `~` 範圍還是 `/` 列舉，見 §13 Q2）。

> 註：LEGACY spec 把此「Jump/OR」列為**未來項（Issue #76）**，但工作表2 已將其**定義為核心邏輯**——本報告以工作表2 為準，視為核心。

## 6. 衍生計算

### 6.1 動作時長
```
Second（動作時長） = 原始秒數 × 系數（寬放係數）
```

### 6.2 機台數／人力 → 動作群組複製、時間分攤
教學檔案的「時間邏輯」區塊（cell C197–C203 ＋示意）：
- 圖示 `A / B*2 / C` → `A + B`：代表**某動作群組依機台數/人數複製**（`*2` ＝複製成 2 份並行）。
- 「**時間邏輯／2 — Follow 機器數的邏輯**」：N 台機台 → 該群組有效時間 ≈ **時間 / N**。
- 「**LB 的邏輯 — 需要增加重複的動作群組**」「如果增加以上則以此類推」。
- 產品 UI（image7）「人數」欄旁註：**「群組的動作需要以人數重複」**。

→ **結論（回應前次 Level Q4）：** 當 cub 區塊超過節拍時，**依機台數/人數把動作群組複製成 N 份並行，有效時間除以 N**。這比先前 CODE 的 `effective_cub_ct = adjusted_ct / max(machines, operators)` 更明確：分攤倍數 N＝複製份數（機台/人數）。**確切 N 的定義（機台、人力、或兩者關係）仍需 User 一句話確認**（§13 Q4）。

## 7. 七個教學範例（逐例，權威驗收集）

> 全部 10 個動作 A~J，每動作 原始秒數=1、系數=1（Second=1），便於聚焦邏輯。

| # | 需求 | 解法（教學原文重點） | 結果（Level / 字符） |
|---|------|----------------------|----------------------|
| **1** | A~J 須依序完成，動作間無綁定，可拆到不同站 | 空白層級表填入對應字符 | A~J 的 main Level = **1,2,3,…,10** |
| **2** | A、B、C 可在前三步互換，其餘 7 個須在其後依序 | 把前三層的數字設為 1 | A、B、C **Level 都＝1**（同層可互換）；D…J ＝2…8 |
| **3** | （承上）要讓 D、E、F 擁有**獨立順序** | D、E、F 用 **sub** 另設；向後延伸一個深度，main 層級後新增 `sub1`，D/E/F 從屬改為 `sub1` | D/E/F 在 `sub1` 群組內以順序欄 1/2/3 排 |
| **4** | （承上）D、E、F 需**不可分割（同站）** | 把功能標籤 `sub1` **改成 `cub1`** | D/E/F → `cub1`（不可拆塊） |
| **5** | B、C 不可分割；D、E、F 成組；**A 可在兩組間跳躍** | B、C 用 `cub1` 設 main=1；D、E、F 用 `sub1` 設 main=2；**A 的 main Level = `1~2`**；其後動作從 main=3 起遞增 | A=`1~2`；B,C=cub1@L1；D,E,F=sub1@L2；G…=L3,4,5,6 |
| **6** | G、H 必須在**不同站別** | G、H 的 **Number 設 `nb1`，Number_Count 設 1**（同站最多 1 個 nb1 → 強制分站） | G,H：Number=nb1, Count=1 |
| **7** | 綜合：A 群組與 B 群組同層；B→C、D→E 在 A 後可互換且各自不可分割；B 組與 D 組不可同站；F→G→H→I→J 順序，G、H 不可分割 | A 用 `sub1` 設 main=1，B、D 設 main=2；B→C 深度3 `cub1`，D→E 深度3 `cub2`；B 組與 D 組 Number 設 `nb1` 數量 1；F 群組深度2 `sub2`，G、H 深度3 用 cub | 多深度 + nb 綜合 |

> 這 7 例（特別是 5/6/7）構成 Level System 邏輯驗證 script 的**黃金測試集**。

### 8.1 合法填寫矩陣（由字符定義推導，✅ 回應 Q1）

> 不必外求；由 §3 四字符定義 ＋ §4 深度模型 ＋「Level System 要讓 IE 填寫不出錯」的目的，即可推導合法/非法規則。欄位語意先釐清：
> - **Ascription = `main` + Level**：此列在**最頂層（main）precedence** 的位置。群組的**頭列**與獨立動作都帶 `main`+Level。
> - **Countersignature = 子群組標籤（sub/cub）+ order**：此列**所屬的子群組**與其**群組內順序**。
> - **Number = `nb`+Number_Count**：橫切的**每站數量上限**。

**填寫規則（R1–R9）：**

| # | 規則 | 違反即非法（image5 對應） |
|---|------|---------------------------|
| **R1** | 每個群組的**頭列**（及獨立動作）必帶 `Ascription=main` + `Level`（數字或範圍） | — |
| **R2** | 群組的**第 2 列起（成員）**只帶 `Countersignature=群組標籤` + `order`，**不得**再自帶 `main`+Level（成員繼承頭列的 main 位置） | **G**：同時掛 main L5 + sub2 →「sub2 重複定義歸屬」 |
| **R3** | 凡屬於某宣告群組的列，**必須**填同一個 `Countersignature` 標籤（不可空） | **C**：Countersignature 空白 →「歸屬不明」孤兒 |
| **R4** | `Countersignature` 只能是 sub/cub 標籤；**main 永遠不可**作為歸屬/從屬名稱（main 只在 Ascription） | — |
| **R5** | `sub`：成員同組但**整組可移動**，內部以 `order` 定序；`cub`：成員**強制同站**、站內順序固定 | — |
| **R6** | **nb 不可與 cub 矛盾**：同一 cub 區塊內的多個成員，不可帶會把它們**拆到不同站**的 nb（cub 要同站、nb count< 成員數要分站 → 衝突） | **H/I**：同屬 cub1 卻各帶 nb1 count1 →「cub 內又加分割」**衝突** |
| **R7** | `Level` 為正整數，或變動值：`~` 範圍（`1~2`）/ `/` 列舉（`1/3`）；**可跳號**；沿表**非遞減**（容許相等＝並行） | — |
| **R8** | 每個 sub/cub/nb 標籤**唯一定義一次**（不可一個標籤指兩個不同群組） | — |
| **R9** | 深度巢狀（**已實作**，C2 拍板）：用 `countersignature`（本列最內層群組）+ `parent_countersignature`（外層群組）兩欄編碼。**只允許 sub⊃cub**（深度上限 main→sub→cub）。引擎細則：`R9_SUB_NESTED`（sub 不可有 parent）、`R9_NEST_ILLEGAL`（cub 的 parent 必為 sub）、`R9_PARENT_MISSING`（parent 群組不存在）、`R9_PARENT_INCONSISTENT`（同群組各列 parent 不一致） | 範例 7 sub⊃cub |

> 三個 image5 紅字標註全部能用 R2/R3/R6 解釋——它們是**反例（IE 易錯點）**，正是 Level System 要擋下的填寫錯誤。
> **正確版（修正 image5）：** C 補 `Countersignature=sub1,order=2`；G 二選一（main L5 獨立 **或** sub2 order3 繼承 E）；H/I 若必須同站則移除 nb1（或把 nb1 count 設 ≥ 區塊成員數）。

## 9. 產出 → Line Balance（產品實況）

由產品截圖（image6/7/8）確證的 LB 介面與行為：

| 項目 | 實況 |
|------|------|
| **Takt（節拍）輸入** | UI 欄位「**單站 CT 上限（秒）**」由使用者輸入（例 16、14）→ **回應 Level Q3：Takt＝使用者輸入** |
| 機種選擇 | 下拉（例 `HDL5X_AVERY05`、`HDL5X_STANDARD`） |
| 計算輸出 | **最佳分站**長條圖（站別1…N，每站堆疊各動作時間）＋ **LBR（Line Balance Rate，例 77.9%）** |
| 下載 | 「下載 MI」按鈕 |
| 失敗案例 | 單站CT上限過小（例 14s）時跳「**計算失敗**」→ 需處理不可行（節拍太小/cub 超節拍無法分站）的錯誤回饋 |

對應後端 `most_engine.level.build_output` 產出的**完整約束模型**（給 LB 演算法；**不塌縮自由度**）：
- **`nodes`**：每節點含 `level`（原字串）+ `levels`（允許主序集合）+ `level_min`/`level_max`/`variable`
  → `1~2`/`1/3` 的「可挪動」自由度完整保留，LB 在集合內擇優；固定整數＝硬約束。
- **`groups`**：每組 `{label, type(sub/cub), parent, same_station, movable, members(已定序)}`
  → cub=同站不可拆、sub=可移動·內部定序、`parent`＝巢狀(sub⊃cub)。另有 `sub_groups`/`cub_groups`/`group_parents` 便利視圖。
- **`number_constraints`**：`{nb: {kind:'max_per_station', limit, members}}` → 不可同站/分站上限。
- **`precedence_edges`**：以 `level_min` 推得的保守先後（便利視圖；真正自由度看 `node.levels`）。

匯出載體：**Excel** 在 MOST 七格後附「主序Level／角色（主/屬）／群組／巢狀母組／組內序／不可同站nb／nb上限」欄（人看得懂關係）；**lb-csv** 含上述全欄＋`level_min/level_max/variable`；**lb-api** 直送 `build_output`（待 LB request model 對映）。

需求清單第 1 點亦要求：**「都一定產出一個 LB ＋限制線」**、第 2 點「**需要指出超過限制的列數**」。

## 11. 「order」欄與產品 UI 欄位（image7）

產品實際 Level System 表（`HDL5X_AVERY05`）欄位：
`MI ｜ CT(秒) ｜ 難度系數 ｜ 調整CT(秒) ｜ Number ｜ main ｜ order ｜ cub ｜ 人數 ｜ 狀態`

- **`order` 欄 ＝ 教學檔案的「群組內順序（depth order）」**（✅ User 2026-06-16 確認）：sub/cub 群組內各成員的先後（1、2、3…），與 `main`（頂層 precedence）分開。
- `cub` 為勾選欄；`人數` 對應機台/人力複製（§6.2）。

### 11.1 產品 UI 互動（v2 workbench Tab②，2026-06-20 定）
教學/image5 的「逐欄手填 Ascription/Level/Countersignature/order」是**規格表示法**，但讓 IE 直接手填正是 image5 三個紅字錯誤的來源。產品 UI 改為**巢狀群組盒 + 拖曳**（參照 Airtable/Notion 的「篩選條件群組」「盒中盒」範式，使用者一看即懂）：
- **拖卡片進群組盒**＝分組；**盒中盒**＝巢狀（sub 盒內可開「＋ cub 子群組」）。藍盒＝sub（可移動），橘盒＝cub（同站不可拆）。
- 系統**自動推導** `Ascription`（群組首列＝main、其餘＝空）、`order`（盒內順序 1..n）、`parent_countersignature`（cub 所在 sub）——IE 不手打，從根本消除 R2/R3/R8/R9 類填寫錯誤。
- **空 sub 只含一個 cub**：deriveLevel 自動攤平（`parent=null`），避免送出引擎看不到的母群組而誤判 `R9_PARENT_MISSING`。
- **nb 是跨樹約束（非層級）**：獨立「約束區」以晶片表達「不可同站」，不塞進樹裡——這正是舊版 R6 與樹衝突的根因。
- 即時呼叫 `/level/validate` 跑 R1–R9。
